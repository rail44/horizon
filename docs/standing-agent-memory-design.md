# 常設エージェントの記憶モデル — ターン毎の「要約+本文」集約

Status: **decided 2026-08-15(オーナー承認 — board #36)**。判断3点
すべて確定。判断点2(集約を書く主体)は外部実績の定量調査
(`docs/research/standing-agent-memory-evidence-2026-08-15.md`、以下
「evidence doc」)を経て決定した。
前提となる決定: 相談の場は board コメント上(#34、オーナー 2026-08-13)、
起床機構は #35 として実装中で wake action は差し替え可能な口(オーナー
2026-08-14)、Tier 2 状態要約は保留続行(`agent-compaction-design.md`
Status、board #37 の field 実測、オーナー 2026-08-14)。

## 問題と仮説

常設エージェント(keeper、#34 の相談役)は board コメントで応答する
非同期の役だが、都度 spawn では文脈が毎回ゼロになる。オーナーの指摘と
仮説(2026-08-14、board #35 の相談中):

> 文脈を持ち越す必要がないというのが誤りで、プロジェクトの進捗状況を
> 把握するのに継続したコンテキストが必要だと思います。
> ただしそれはコーディングのようなフルの作業ログではなく、ターン毎に
> 要約と本文の形への集約を行った上で保持すればいいのではないかという
> 仮説があります。

つまり常設エージェントの記憶 = 生の作業ログではなく**濃縮された履歴**。
本 doc はこの仮説を実装可能な形に落とし、決定が要る点を推奨付きで並べる。

## 決定(3点)

### 1. 集約の置き場所 — 決定: イベントログ内のターン集約イベント+送信時投影(オーナー 2026-08-14)

**A 案(決定)**: ターン終了時に `TurnDigest` イベント(要約 1〜3 行+
構造化された本文+畳んだ生ログ範囲への参照)を event log に追記する。
provider へ送る履歴の組み立て時に、過去ターンの生の往復を digest で
置換する — 組み立ては `[brief 原文][digest 列][直近 tail 原文]`。

- **Tier 1 が確立した投影方式の踏襲**: event log・DuckDB は無傷のまま、
  provider 送信時にのみ変換する(`providers/rig/clearing.rs` と同じ
  「1 call site の 1 関数」の継ぎ目)。正本は常に log — logd 設計の
  原則と整合。
- **digest が永続データになる**: #13(restore/fork)と #35 の wake が
  そのまま消費できる。プロトコルバンプ等でセッションが失われても、
  後継セッションを digest 列から種付けできる — 常設エージェントの
  「個体」がセッション id ではなく digest 列になり、セッションは
  使い捨て可能になる。
- **透明性**: 集約の区切りを transcript に表示できる(Tier 1 と同じ)。

**B 案(対案・暫定としては併用可)**: 外部文書方式。keeper は都度 spawn の
まま、走行の終わりに knowledge 層(`knowledge.write` —
`$XDG_DATA_HOME/horizon/knowledge/`)の記憶文書を更新し、次回 spawn が
最初に読む。

- 利点: agent コア変更なしで今すぐ動く。記憶が人間可読・編集可能。
- 欠点: 記憶が event log の外に二重化する。品質防御(膨張・崩壊)を
  スキル遵守頼みで再発明することになる。#13 に寄与しない。
- 位置づけ: A 案が着地するまでの暫定運用としては有効(スキルの追記
  だけで実現できる)。恒久機構としては採らない。

### 2. 集約を書く主体 — 決定: エージェントが書く。構造と頻度はハーネスが保証する(オーナー承認 2026-08-15)

外部実績の調査(evidence doc)の結論: 主体の二択を直接支持する数値は
文献に存在せず、証拠が収斂しているのは形 — 増分更新・構造化・不変部分の
pinning・**書き込みの選別**(無選別 −12.05pp vs 選別 +3.42pp)・生ログ
非破壊。この形を満たす配置として:

- **記憶の更新は型付きツール**(`memory.update` 相当)。入力スキーマ
  そのものが構造化テンプレート(Tier 2 由来: goal / 決定 / 完了・進行・
  詰まり / 次の一手 / 関係ファイルとシンボル、+ 畳んだ生ログ範囲への
  参照)。形式のドリフトをスキル遵守でなくスキーマで構造的に排除する。
  更新は**フィールド単位の増分**(追記・訂正・削除)— 全文の再生成は
  1 回でも崩壊しうる(ACE 66.7→57.1%、codex#14589 のトークン残存
  13.7%→6.9% — evidence doc §2-1)。
- **ターン末チェックポイント(機械的検査、LLM 呼び出しなし)**: 常設
  ロールのターンは「memory を更新した」か「更新不要を理由付きで明示
  した」かでしか終われない。エージェント方式の最大リスクである無言の
  書き忘れを構造的に不可能にする。
- **中身の取捨はエージェントに残す**: 選別が実証された品質レバーで
  あり、何が重要かは文脈の中の本人が最もよく知る。ハーネス強制要約は
  毎回の出力を強いられ、反復再要約の崩壊・平板化の実測がある失敗形に
  入る。較正材料として、この開発体制の integrator 自身の memory 運用
  (構造化ファイル・選別書き込み・自己訂正)が同型で実働している。
- **撤退線**: digest は event として永続し投影で消費される(決定 1)
  ため、エージェント自筆が dogfood で不十分と実測されたら、同じ
  イベント形の裏でハーネス発行の要約リクエスト(旧案)に差し替え可能。
  購読・投影・#35 の wake 側は変更不要。
- **リスク(明示)**: 書く品質のモデル依存(evidence doc §3 — 書き
  すぎる/書かないがモデル依存で実在)と、選別の失敗(重要事項を
  「更新不要」と判断する)。どちらも dogfood(keeper 運用)で測る。

適用対象は**常設ロールに限定**(`RoleDefinition` にフラグを足す)し、
コーディングセッションには入れない。

### 3. Tier 2 との関係 — 機構は流用、目的とトリガーは別物

Tier 2 は窓圧力駆動(80%)の生存機構で、board #37 の実測により動機が
休眠と確認され保留続行(オーナー判断 2026-08-14)。本件は**常設ロール
限定・毎ターンのチェックポイント付き**の記憶モデルであり、Tier 2 の
順序決定(「計測後に着手」)の射程外(オーナー整理 2026-08-14)。
テンプレートの構造と防御(膨張破棄・失敗ラッチ)の考え方は Tier 2 設計を
流用するが、発火条件と適用対象が独立。
将来 Tier 2 を実装する判断になった場合、本機構の運用実績が Tier 2 の
実測済みの土台になる(証拠の逆流)。

## #35(起床機構)との接続

#35 の wake action は差し替え可能な口として実装される。v1 = keeper を
都度 spawn。本設計が着地したら v2 = 「digest 列を持つ常設セッションの
再開(セッションが失われていれば digest 列からの種付け spawn)」を
その口に差す。購読・policy 側は変更不要。

## 未決・実測項目

- **digest の品質と減衰曲線は dogfood で測る**: keeper / #34 相談役の
  運用で「集約だけで進捗把握が足りるか」「数十〜数百回の反復で劣化
  するか」を見る。毎ターン級の反復領域の品質減衰曲線は文献に存在せず
  (evidence doc §1)、この運用が最初の実測になる。足りなければ
  テンプレートを直す(形の議論を先にしない)。
- ツールスキーマの初期値は Tier 2 のテンプレートをそのまま使う。
- 常設ロールのフラグ名・チェックポイントの実装形・「更新不要」の
  理由の粒度は実装時判断。
