# 常設エージェントの記憶モデル — ターン毎の「要約+本文」集約

Status: **draft 2026-08-14(integrator 起草、オーナーレビュー待ち — board #36)**。
前提となる決定: 相談の場は board コメント上(#34、オーナー 2026-08-13)、
起床機構は #35 として実装中で wake action は差し替え可能な口(オーナー
2026-08-14)、Tier 2 状態要約は保留続行(`agent-compaction-design.md`
Status、board #37 の field 実測、オーナー 2026-08-14)。

## 問題と仮説

常設エージェント(keeper、#34 の相談役)は board コメントで応答する
非同期の役だが、都度 spawn では文脈が毎回ゼロになる。オーナーの指摘と
仮説(2026-08-14、board #35 の相談中):

> 文脈を持ち越す必要がないというのが誤りで、プロジェクトの進捗状況を
> 把握するのに継続したコンテキストが必要だと思います。
> ただしそれはコーディングのようなフルの作業ログではなく、ターン毎に
> 要約と本文の形への集約を行った上で保持すればいいのではないかという
> 仮説があります。

つまり常設エージェントの記憶 = 生の作業ログではなく**濃縮された履歴**。
本 doc はこの仮説を実装可能な形に落とし、決定が要る点を推奨付きで並べる。

## 決めること(3点)と推奨

### 1. 集約の置き場所 — 推奨: イベントログ内のターン集約イベント+送信時投影

**A 案(推奨)**: ターン終了時に `TurnDigest` イベント(要約 1〜3 行+
構造化された本文+畳んだ生ログ範囲への参照)を event log に追記する。
provider へ送る履歴の組み立て時に、過去ターンの生の往復を digest で
置換する — 組み立ては `[brief 原文][digest 列][直近 tail 原文]`。

- **Tier 1 が確立した投影方式の踏襲**: event log・DuckDB は無傷のまま、
  provider 送信時にのみ変換する(`providers/rig/clearing.rs` と同じ
  「1 call site の 1 関数」の継ぎ目)。正本は常に log — logd 設計の
  原則と整合。
- **digest が永続データになる**: #13(restore/fork)と #35 の wake が
  そのまま消費できる。プロトコルバンプ等でセッションが失われても、
  後継セッションを digest 列から種付けできる — 常設エージェントの
  「個体」がセッション id ではなく digest 列になり、セッションは
  使い捨て可能になる。
- **透明性**: 集約の区切りを transcript に表示できる(Tier 1 と同じ)。

**B 案(対案・暫定としては併用可)**: 外部文書方式。keeper は都度 spawn の
まま、走行の終わりに knowledge 層(`knowledge.write` —
`$XDG_DATA_HOME/horizon/knowledge/`)の記憶文書を更新し、次回 spawn が
最初に読む。

- 利点: agent コア変更なしで今すぐ動く。記憶が人間可読・編集可能。
- 欠点: 記憶が event log の外に二重化する。品質防御(膨張・崩壊)を
  スキル遵守頼みで再発明することになる。#13 に寄与しない。
- 位置づけ: A 案が着地するまでの暫定運用としては有効(スキルの追記
  だけで実現できる)。恒久機構としては採らない。

### 2. 集約を書く主体 — 推奨: ハーネス(Tier 2 方式の要約リクエスト)

ターン終了時に**ハーネスが**同一モデル・同一 prefix で構造化テンプレート
の要約リクエストを発行する。テンプレートと防御は Tier 2 設計
(`agent-compaction-design.md`)をそのまま流用:

- テンプレート: goal / 決定 / 完了・進行・詰まり / 次の一手 / 関係
  ファイルとシンボル(エラーは逐語)。既存 digest があれば **iterative
  更新**(再要約の重ね掛けは Codex 実測の崩壊経路)。
- **参照付き**: digest は畳んだ生ログ範囲への参照を必ず含み、詳細は
  recall で再取得可能と本文に明示。
- 防御: 要約が元より膨張したら破棄、失敗したらラッチ。
- コスト: ターン毎に 1 要約リクエスト(同一 prefix なので cache read で
  安価 — Tier 2 設計の同一モデル・同一 prefix 論と同じ根拠)。

エージェント自身にターン末で書かせる案は採らない: 書き忘れ・形式逸脱が
スキル遵守頼みになる。決定的に走るハーネス側に置く。適用対象は**常設
ロールに限定**(`RoleDefinition` にフラグを足す)し、コーディング
セッションには入れない。

### 3. Tier 2 との関係 — 機構は流用、目的とトリガーは別物

Tier 2 は窓圧力駆動(80%)の生存機構で、board #37 の実測により動機が
休眠と確認され保留続行(オーナー判断 2026-08-14)。本件は**常設ロール
限定・毎ターン無条件**の記憶モデルであり、Tier 2 の順序決定(「計測後に
着手」)の射程外(オーナー整理 2026-08-14)。要約リクエストの形・
テンプレート・防御は Tier 2 設計を流用するが、発火条件と適用対象が独立。
将来 Tier 2 を実装する判断になった場合、本機構の運用実績が Tier 2 の
実測済みの土台になる(証拠の逆流)。

## #35(起床機構)との接続

#35 の wake action は差し替え可能な口として実装される。v1 = keeper を
都度 spawn。本設計が着地したら v2 = 「digest 列を持つ常設セッションの
再開(セッションが失われていれば digest 列からの種付け spawn)」を
その口に差す。購読・policy 側は変更不要。

## 未決・実測項目

- **digest の品質は dogfood で測る**: keeper / #34 相談役の運用で
  「集約だけで進捗把握が足りるか」を見る。足りなければテンプレートを
  直す(形の議論を先にしない)。
- テンプレートの初期値は Tier 2 のものをそのまま使う。
- 常設ロールのフラグ名・粒度は実装時判断。
