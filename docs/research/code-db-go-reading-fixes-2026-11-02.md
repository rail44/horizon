# コードデータベース:実在の Go リポジトリでの読み合わせと、その修正(2026-11-02)

別のセッションが、code-db(`main` 7085a748)を非公開の Go モノレポ 1 件で動かした。報告は件数、分類、自作の最小例だけで、対象のコードやパスは含まない。規模は、範囲内の Go ファイル 4,897(約 119 万行)、モジュール 28、パッケージ 816、units 37,277、unit の辺 86,715。`code-db index` は 653 秒でエラーなく終わった。手で読んだ 20 件は、範囲、kind、qualified_name、parameters、visibility、is_test、member_of、entry がすべて正しく、誤りはテスト関数の状態だけだった。

## 1. 報告された不具合と修正(オーナーの判断:1〜6 を直す)

1. **16 MiB を超える jscpd のレポートで、読み込みが止まる。** jscpd のレポートは全体が一つの JSON オブジェクトで、`read_json` は既定で 16 MiB(`maximum_object_size`)を超えるオブジェクトを読まない。この規模で exact 37 MB、normalized 101 MB になり、`clone_report_pairs` を読むすべてのクエリが失敗した。修正:`00_load.sql` で、レポートの最大サイズ(既定の 16 MiB 未満なら 16 MiB)を `clone_report_bytes` に入れ、`read_json` の `maximum_object_size` にする。`read_blob` はサイズだけを読む。
2. **duplication がメモリ上限で失敗する。** clone_pairs 58,534 件で、`clone_pairs` を一つの計画の中で二度(直接と `clone_sides` 経由で)評価すると、上限を越えた(報告側は一時表に写して回避)。修正:`refresh.sql` が `clone_pairs` と `clone_sides` もキャッシュに写す。jscpd のレポートの内容もキャッシュの鍵に入れた。`code-db index` は索引とレポートを同時に書き直すので、鍵が変わる時期は今までと同じ。
3. **Go のテスト関数が `test` にならない。** scip-go は、`go test` が作るテスト用 main(Go のビルドキャッシュにある文書)も索引し、それがすべての `TestXxx` を参照する。そのため、テスト関数 4,586 件がすべて `referenced` になった。また、モジュールがリポジトリ直下にないと、文書は `sub/../../…/go-build/…` と名付けられ、`../` で始まらない。修正:
   - `views/scip.sql` の文書のパスを `normalized_path`(`.` を落とし、`..` で前の段を消す)で正規化し、リポジトリ外の文書が `../` で始まるようにした。
   - `unit_reference_status` は、リポジトリ外の文書からの参照を数えない(除外したファイルからの参照は今までどおり数える)。cgo の生成ファイルからの参照も数えなくなるが、cgo のファイルはもともと制限として units を持たない。
4. **パッケージ水準の `var` の中の関数リテラルの引数が、unit になる。** scip-go は、関数の外にある関数リテラルの引数や変数を、`local` ではなく `…/hooks:n.`(Variable)と名付ける。同じ名前は一つの記号になり、範囲は外側の `var` と同じになる。unit の約 2.7%(1,000 件)がこれで、曖昧な記号 70 と、同じ範囲の組 178 のほとんどの原因だった。修正:`go_units` は、最後の記述子が `:` を含む Variable を unit にしない。
5. **外部テストパッケージで、Go にない循環が出る。** `package x_test` のファイルがディレクトリのパッケージにまとめられていたため、「外部テストが、テスト対象を import するパッケージを import する」という合法の形が循環に見えた(7 循環すべて)。修正(推奨した形):パッケージ節が `_test` で終わる `_test.go` のファイルは、パッケージ `<ディレクトリ>_test` にする。`namespace_path` はディレクトリのままなので、テスト対象への辺は入れ子の辺(構造上のもの)になる。
6. **大きな結果で並び順が崩れる。** code-db はクエリの結果を一時表に入れ、表示名に置き換える SELECT(`display_select`)で出す。語彙の列の `display_term` はサブクエリで、二つの語彙の列があると、その結合が行の順序を崩した。一時表の中の順序は保たれていた。Horizon のルートでも `size` で再現した(先頭に 3 行の unit)。修正:`display_select` が一時表の `rowid` で並べる。

## 2. 残したこと(オーナーの判断待ち)

- 同じリポジトリの別モジュールを公開タグ版で require すると、version が食い違い(タグ版とコミットハッシュ)、モジュール間の参照がすべて切れる。そのため `coupling level=module` は全部 0 だった。
- 受け手の型が除外したファイル(生成コード)にあると、`member` の事実が NULL になる(2,135 件)。
- 層のパターンの GLOB で、`*` が `/` を越える。
- 小さなもの:`testdata/` とモジュール外のファイルに units がないことの文書化、scip-go の並列実行、darwin-arm64 でのリファクタ監査の setup(jscpd のビルド済みバイナリがない)、`DUCKDB_CLI` の既定値。
- 解析用のプロンプトの誤り:Go のファイル単位は `unreferenced` に出る、と書いたのは誤りだった。import がパッケージの記号を参照するので、`referenced` になる。

## 3. 確認

- 1:36 MB のレポート(90,000 件)を、修正前は読めず、修正後は読めた。`check.py` のフィクスチャの normalized レポートに 17 MiB の statistics を足した。

- 3〜5:code-db の end-to-end テストに、モジュールをサブディレクトリに置き、内部と外部のテストパッケージ、パッケージ水準の `var` の関数リテラルを持つフィクスチャを足した。テスト関数は `test`、リポジトリ外の文書は `../` で始まり、`hooks:n` は unit にならず、外部テストは `sub/a_test` で、循環は出ない。

- Rust:Horizon のルートの索引で、22 の層を変更前と比べて差 0 行。
- `duckdb-ext/check.sh`(end-to-end テストは scip-go ありで 4 件)、`check.py fixture` が通った。
