# マイルストーンから実装まで — 最初の検証の設計

2026-09-13。方向性の合意を受けた設計案。今回作ったのは仕様と画面試作であり、Horizon 内の自動実装機能ではない。

## 操作して確認する

[画面見本を開く](../assets/board-milestone-flow/index.html)。ローカルのブラウザで開ける。ネットワーク接続やビルドは不要。

実ボードの #46「daemon が作成したセッションに shell から到達できない」を題材にした模擬シナリオ。ID指定で開く修正と一覧への反映の順序を相談し、計画へ反映する例になっている。この例で人間への相談を必須にするという仕様ではない。実ボードへの書き込みやエージェントの起動は行わない。

上部の見本用操作で、計画、実装、検証失敗、再試行、検証済み、統合後の状態を進められる。製品側の画面では現在地と次の作業が変わる。失敗しても成功表示にならず、一部が統合されてもマイルストーン全体は完了にならない。

自然言語の返答欄も置いた。見本には言語モデルがないため、自由な返答は受領した内容として保持し、勝手に案の採用へ変換しない。「返答を受け取った」と「意図を理解して計画に反映した」は異なる状態である。

## 必要な機能を実装単位にする

| 順序 | 作るもの | 使えると判断する条件 |
|---|---|---|
| 1 | 目標・達成条件・作業・判断の保存と操作 | 既存項目を整理でき、判断を記録・再検討でき、再起動後も同じ状態へ戻れる |
| 2 | 目標から計画と未決事項を作る処理 | 人間が履歴を読み直したりタスクを手で書き直したりせず、次に進める仕事が分かる |
| 3 | 実行可能な作業とエージェントの接続 | 文脈を転記せずに実装が始まり、セッションを開け、停止・失敗・再起動を追跡できる |
| 4 | 検証・統合・残作業の反映 | 実行終了を完了と取り違えず、実際の成果で達成条件と次の作業が更新される |
| 5 | 複数目標と並列実行の調整 | 目標の順位、依存、共通作業、競合から次の実行が予測可能に決まる |

最初の実検証には 1〜4 が必要。親子フィールドだけ、要約画面だけ、エージェントの起動だけの完成を、自動で一巡する状態の完成とは数えない。

## 人間向けの表示

常に見えるのは、目標、達成条件、現在地、未決の判断、次に進む作業と理由。調査の過程、全コメント、失敗した試行のログは詳細へ退け、根拠は辿れるようにする。

判断事項には、何が未決か、なぜ今必要か、選択肢と影響、推奨と理由、影響する作業を持たせる。調査すれば分かることは調査へ回し、既に決まったことや同じ問いを繰り返し並べない。仮定をオーナーの判断として記録しない。

## 自動実行で守る状態の区別

- 作業の開始と、実際のセッション起動。
- 返答の受領と、解釈・計画への反映。
- エージェントのターン終了と、作業の完了。
- ブランチ上の検証成功と、main への統合。
- 一部の作業完了と、マイルストーンの達成。
- 新規着手の一時停止と、動いているセッションの終了。

main への統合は、現在のリポジトリの指示どおりオーナーの明示的な許可を要する。通常の計画・実装に新しい承認手順を追加する提案ではない。

## 次に実装する部分の境界

最初の実装は、目標・判断・作業の更新を保存し、現在の計画を画面から操作できるところ。スキーマ変更だけで終わらず、実際の既存項目を移動して、判断が解消したら表示と作業の待ち理由が変わるところまでをまとめて確認する。

その上に計画生成と実行をつなぐ。現在の Keeper はコメントによる文脈補完の役であり、計画を維持して実行を回す役が存在することにはならない。役ごとに新しい常設エージェントを増やすかどうかは未決。

詳細な状態・操作・実装担当箇所・受け入れ条件は [設計書](../board-milestone-flow-design.md) に記載。

## 今回の検証記録

- Chromiumで操作を検証。判断の反映と履歴化、自由な返答の受領、入力途中の文章の保持、新規着手の停止中の結果受信、検証失敗と再試行、検証と統合の区別、未実行タスクへの結果の誤表示防止、部分完了を確認した。画面幅1440pxと390pxの表示も確認。これは試作の動作確認であり、実際の使いやすさや実エージェントの実行を検証したものではない。
- `cargo fmt`、workspace全対象のclippy、sandboxed nextest（1,873件成功）、wire-schema checkerが通過。
- 設計ブランチは既存の品質ゲート修正 `board-47-gate`（`306a06a`）上に積んでいる。今回追加した変更は文書とHTMLのみ。mainと実ボードの状態は変更していない。
- 新規worktreeの通常ビルドは容量不足で中断したため、その生成物だけを削除して再実行した。最終ゲートでは `CARGO_PROFILE_DEV_DEBUG=0`、`CARGO_PROFILE_TEST_DEBUG=0`、`CARGO_INCREMENTAL=0` を使用し、テストの除外追加や他worktreeとのビルド成果物共有は行っていない。
