# リファクタリング対象の初回確認

基準は `e3c619a0`。全体解析は通常実装335ファイル・2,525関数を対象とした。
数値の大きさに加え、呼び出し元・同じ責務の実装・既存テストを確認した。

| 対象 | 根拠と判断 | 対応 |
| --- | --- | --- |
| `src/runtime/mod.rs` の同期要求 | ast-grepの待機箇所8件のうち7件が、同じキュー送信・応答待機契約。停止と時間切れの実装を個別に維持していた | `request.rs` に集約。60秒の待機、要求ごとの応答経路、既存の診断文とdaemonの戻り値を維持 |
| agent/terminalの `establish_for_drain` | jscpdで検出した重複。型以外は同じ初期化・期限・失敗時のタスク破棄 | `common.rs` の型付き関数に集約 |
| agent/terminalの接続復旧ループ | 大きな重複だが、版拒否時の復旧予算やterminalの破壊的なdrainが異なる | 判断部分は維持。今回の共通化に含めない |
| `tools/catalog.rs::definitions` | RCAで760行。ただし主体はツール定義とJSON schemaの列挙 | 行数だけを理由に分割しない |
| `horizon-logd::writer::perform` | RCAのcognitive値78。ファイルロック・履歴のfold・要求別検証・追記が一関数にある | 次の調査対象。検証とイベント生成を分けられるか、原子性と冪等性のテストから確認する |

端末の一括attachは全要求を送信してから応答を回収するため、単一要求の
ヘルパーに置き換えない。待機の時間切れは、送信済み要求のキャンセルを意味しない。

ツール自体は、通常実装に混ざっていたGUI E2Eテストの分類を修正した。
`e2e.rs` の補助関数と `gpui::test` をテスト側へ分類し、回帰テストを追加した。
