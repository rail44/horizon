# UI の土台の候補調査(2026-11-11)

Horizon の画面全体の土台を gpui から置き換えるとしたら何がありうるか、の調査記録。
置き換えるかどうかの判断はここでは行わない。

## 調査の観点

きっかけは、gpui の状態更新(`notify` でビュー単位に描き直す)への不満と、記事
[A Critique of GPUI](https://blog.zortax.de/posts/a-critique-of-gpui)(2026-11-08)。
求めているものは次の 4 つ。

1. 状態: 一度だけ走るコンポーネント+signal(読んだ場所だけが更新される)
2. スタイルとレイアウト: CSS 的に書けること
3. 増分更新: 状態だけでなく、レイアウトと描画も変わった部分だけで済むこと
4. gpui-component が埋めていたもの(テキスト入力と IME、ボタンやモーダルなどの部品)を誰が持つか

記事の要点は「signal にしただけでは速くならない。レイアウトと描画が全体を走査するなら、そこで時間を使う」。
したがって 3 を、状態・レイアウト・描画の 3 段に分けて見る。

## 確かめ方と確かさ

- **機械的に取ったもの**: GitHub API による活動状況(2026-11-11 取得)、crates.io の公開日。
- **一次情報を読んだもの**: 各リポジトリの README、設計文書、`Cargo.toml`。
- **こちらで動かして確かめたものは無い。** 性能と機能についての記述は、各プロジェクト自身の説明か、上の記事の計測による。
  記事の計測は著者(zgui の作者)の未公開ハーネスによるもので、各フレームワークの作者のレビューを受けていない(記事自身の記載)。

## 候補ごとの記録

### zgui(zortax/zgui)

求めている 4 点すべてに、説明の上では当たる。上の記事の著者のフレームワーク。

- **構成**(README): 「components + reactive_graph signals → retained document → Stylo cascade → cephal layout + Parley text → retained paint recordings → wgpu renderer + Vello → persistent render target」。
  各段が「次の段に、やるべき仕事だけを渡す」と説明している。
- **状態**: Leptos の `reactive_graph`(`=0.2.14` で固定)。仮想 DOM なし。コンポーネントは一度だけ走る。
- **CSS**: Stylo(`=0.19.0` で固定)。セレクタ、カスケード、カスタムプロパティ、メディアクエリ、flexbox、grid、遷移、アニメーション。
  `docs/parity.md`(生成物)によると、エンジンが持つ 250 のロングハンドのうち 179 を実装、71 は解析とカスケードのみ。
  `:has()` などは Stylo の servo ビルドの制約で使えず、フォークはしない方針と書いている。
- **レイアウト**: `cephal` 0.2.0(同じ作者、crates.io に 2026-10-10 公開)。「Retained, incremental CSS layout (block, flexbox, grid) with spineless invalidation」。
  過去の検索結果には「Taffy for layout」とあり、途中で置き換えた形跡がある(経緯は確かめていない)。
- **描画**: wgpu 29、Vello 0.9。フレームをまたぐ描画先を持ち、損傷矩形の外のピクセルは前の値を保つ、と説明。
- **部品**: `zgui-ui` に input、textarea、select、combobox、dialog、popover、menu、tabs、sidebar、data_table、toast、tooltip、resizable、scroll_area、virtualize など約 60。
- **入力**: IME の前編集(preedit)を扱うコードが `zgui-input` と `zgui-edit` にある。
- **プラットフォーム**(README): Windows、macOS、Linux(Wayland と X11)、headless。アクセシビリティ(AccessKit)、クリップボード、複数ウィンドウ、独自のウィンドウ装飾。
- **独自の描画**: canvas、SVG、カスタム要素、アプリケーションのシェーダ、wgpu の面の埋め込み。
- **テスト**: headless のプラットフォームと testkit のクレートがある。性能は `cargo xtask perf` が CI の一部で、帯を外れると失敗する(`docs/performance.md`)。
- **この上で作られたもの**(README): コードエディタ(zdt: 分割、ファイル木、LSP、Git、ターミナル、コーディングエージェントのワークフロー)、
  埋め込み用のターミナルエミュレータ(zgui-terminal)、埋め込み用のコードエディタ(zgui-editor)、Spotify クライアントなど。
  いずれも同じ作者か近い人のもので、zdt と zgui-terminal と zgui-editor は 2026-09 以降の push がない。
- **見当たらなかったもの**: Markdown を表示する部品(リポジトリ内の検索で該当なし)。`wasm32` 向けの対応。

リスクとして読み取れること。

- 作成から 3 か月(2026-08-02)。v0.1.0 が 2026-10-15。README に「experimental and changes often. Expect breaking changes between 0.x releases」。
- コミットの大半が 2 人(636 と 181)。
- 開発は nightly(`nightly-2026-04-16`)。公開クレートは stable(`rust-version = "1.90"`)でビルドできると書いている。
- Stylo と `reactive_graph` を完全一致で固定している。fontique は `vendor/` に持っている。
- リポジトリに `CLAUDE.md` がある。

### Floem(lapce/floem)

以前使っていた土台。離れた理由の一つだった上流の更新は、今も遅い。

- 直近 90 日のコミットは 1 件(2026-09-24)。その前は 2026-06-21、2026-05-11。最新リリースは 2024-11-15 の v0.2.0。
- README: ビューの木は一度だけ作る。レイアウトは Taffy。描画は vger、vello、Skia(AnyRender)、tiny-skia から選ぶ。
- 記事の計測: ラベル 1 つの変更で、反応の処理は 0.01ms、その後のレイアウトに約 14ms(3,000 行)。
  「Taffy does not know that one leaf moved」。同じ変更が再描画されない既知の不具合がある、とも書いている。

### Blitz + Dioxus Native(DioxusLabs/blitz)

HTML/CSS の描画エンジン。Stylo+Taffy+Parley+Vello という部品の組み合わせは zgui と近い。

- README: 「Blitz is currently in a **beta** state ... usable for making apps if you are an early adopter」。
- 対話できるのは `dioxus-native`(Dioxus の仮想 DOM を描く)経由。Dioxus は signal を持つが、コンポーネントを再実行する型。
- `blitz-dom` を土台にして、状態の層だけ別のもの(一度だけ走る signal)を載せる、という使い方は README からは読み取れない(確かめていない)。
- Markdown と HTML を表示するフロントエンド(`blitz`)があるが、対話はできないと書いている。

### Freya(marc2332/freya)

- 状態は signal だが、コンポーネントを再実行する(`use_state`)。記事は「細かい更新には小さいコンポーネントが要る」点を gpui と同じ問題として挙げている。
- 記事の計測: 3,000 行でキー入力 1 回が 1.2ms。ラベル 1 つで、5 つの変更を出した後に 57,050 のレイアウトノードを訪問。
- 描画は Skia。コードエディタ用の部品(Rope+tree-sitter)がある。

### Xilem / Masonry(linebender/xilem)

- README: 「An experimental Rust architecture for reactive UI」。直近 90 日のコミットは 18 件。
- Xilem はビューの木を作り直して差分を取る型で、signal ではない。Masonry は保持したウィジェット木を持つ下の層。

### Vizia、Slint、Iced

- Vizia: 2026-03 に lens から signal へ移行(記事)。直近 90 日のコミットは 10 件。
- Slint: 活発(2272 件)。独自の言語で書く。ライセンスは GPL・ロイヤリティフリー・商用の選択式(SPDX は NOASSERTION)。
- Iced: Elm 型で、求めている状態モデルと異なる。

### gpui-fast(longbridge/gpui-fast)

gpui を替えずに、同じ問題を軽くする選択肢。

- README: 「GPUI extracted from the Zed monorepo as a standalone workspace, with the layout engine reworked to keep what did not change between frames」。
  変わらないビュー、レイアウトノード、文字計測を再利用する。gpui-kit から使うための互換設定がある。
- 作成は 2026-09-24。直近 90 日のコミットは 336 件。
- 記事の計測: 3,000 行でラベル 1 つが 8.4ms から 3.4ms。状態を各パネルが持つ場合は 83% 減、共有モデルの場合は 11% 増。
- 状態モデルは gpui のまま(最小の単位はビュー)。書き方の問題は残る。

## 追補: 小さなクレートを組み合わせる場合(同日)

zgui は自前で持つ範囲が広い(Wayland・DRM・evdev・libinput・xkb のプラットフォーム層、レイアウト、描画記録、
レンダラ、入力、編集、部品、テスト基盤)。小さな責務のクレートを組み合わせて同じことができるかを調べた。

### Taffy は増分か(こちらで計測)

Taffy 0.15.1 で、行(行 = 伸びるラベル+固定のラベル)を縦に並べた木を作り、ラベル 1 つの文字幅を変えて
`mark_dirty` → 再レイアウトした。release、中央値(51 回)、マイクロ秒。括弧内は文字の計測関数が呼ばれた回数。

| 行(ノード) | 丸めあり・親 1 つ | 丸めなし・親 1 つ | 丸めなし・50 行ごとにグループ | 丸めあり・50 行ごとにグループ |
|---|---:|---:|---:|---:|
| 100(301) | 35.8(9) | 8.4(9) | 10.6(9) | 19.1(9) |
| 1,000(3,001) | 379.9(9) | 72.0(9) | 18.7(9) | 125.6(9) |
| 3,000(9,001) | 561.7(9) | 238.1(9) | 22.7(9) | 373.5(9) |
| 10,000(30,001) | 3607.2(9) | 908.2(9) | 23.3(9) | 1665.7(9) |

何も変えずに再レイアウトした場合は、丸めなしで 0.04(ルートのキャッシュが当たる)、丸めありで 3,000 行のとき約 340。

読み取れること。

- 文字の計測はキャッシュされる。葉 1 つの変更で計測は 9 回で、木の大きさによらない。
- 既定で有効な丸め(`round_layout`)は、全ノードを再帰的に訪問する。`disable_rounding` で外せる。
- 丸めを外すと、時間は「変更箇所の祖先が持つ子の数」に比例する。親 1 つに 3,000 行なら約 240、50 行ごとに分ければ約 20 で、行数によらない。
- 記事が Floem について書いた「ラベル 1 つでレイアウト約 14ms(3,000 行)」は、Taffy 単体のこの値(0.2〜0.6ms)よりずっと大きい。
  差が Floem 側のどこから来るかは調べていない。

計測コードは作業用ディレクトリにあり、リポジトリには入れていない。

### 部品が見当たらないもの

- **損傷矩形と、フレームをまたぐ描画先の保持**: anyrender にも `blitz-paint` にも見当たらない。zgui は自前で持っている。
- **signal と文書の木をつなぐ層**: `blitz-dom` の `DocumentMutator` に signal から書き込む層は、既存のものが見当たらない(Dioxus は仮想 DOM の差分から書き込む)。
- **部品一式**(入力欄、ダイアログ、メニューなど): 土台に依存しない形のものは見当たらない。understory がその下の状態機械(オーバーレイ、フォーカス)を持つ。

### 調べていないこと(追補分)

- `blitz-dom` の増分モードが既定で有効か、どこまで安定しているか。Taffy の丸めを全体で走らせているか。
- Vello の Sparse Strips 方式に、部分的な再描画の仕組みがあるか(コード検索の回数制限で確認できなかった)。
- understory の各クレートの公開状況と API の安定度。
- cephal を zgui の外で使った例があるか。

## 追補 2: 試作(同日、`spikes/ui-foundation/`)

`reactive_graph` で書いた一度だけ走るコンポーネントが `blitz-dom`(0.3.0-beta.4)の文書を書き換える層を作り、
ウィンドウなしで動かした。ここからは、こちらで動かして確かめた結果。

### 確かめられたこと

- **つなぐ層は約 310 行で書けた**(`src/lib.rs`)。要素を作る、属性と文字を signal に追従させる、キー付きリスト、イベントのハンドラ、独自描画の差し込み。
  signal を読むクロージャを effect にして、文書の該当ノードに 1 回書くだけで、差分の計算はリストのキー以外にない。
- **イベントは `blitz-dom` の当たり判定と配送をそのまま通る**。ポインタの押下と解放を座標で与えると、
  ボタンの `click` ハンドラが呼ばれ、signal が書かれ、文字ノード 1 つが変わる(テストで確認)。
- **絵が出る**。CPU レンダラ(vello_cpu)で PNG に書き出して目で確認した。CSS(flex、角丸、枠線、色)、日本語の文字、
  `<input>` と `<textarea>` の初期値が描かれる。入力欄の文字の下端がわずかに切れていた(行の高さの指定の問題と見られるが未調査)。
- **独自描画の口がある**。`blitz_dom::Widget` を要素に付けると、文書がレイアウトした箱の中を自分で描ける
  (描画命令の列を返すか、wgpu のテクスチャを登録する)。セルの格子を手描きして、絵に出ることを確認した。
  `blitz-paint` 側で `custom-widget` の feature を有効にする必要がある。

### 計測

行(行 = signal に追従するラベル+固定の語)を並べ、中ほどの 1 行だけ変えた。release、中央値(31 回)、マイクロ秒。
マシンが混んでいる時間帯の値で、同じ計測の別の回では 3 割ほど小さい値も出ている。

増分レイアウトあり(既定)、全行が 1 つの親の下:

| 行 | signal の書き込み+effect | 文字 1 つ変更後の resolve | 色 1 つ変更後の resolve | 何も変えない resolve | 描画(800×600、CPU) |
|---|---:|---:|---:|---:|---:|
| 100 | 1.7 | 91 | 99 | 32 | 1612 |
| 1,000 | 1.8 | 625 | 594 | 286 | 918 |
| 3,000 | 2.5 | 1915 | 2090 | 938 | 1363 |
| 10,000 | 6.8 | 11062 | 11303 | 8272 | 1299 |

50 行ごとにグループに分けた場合、3,000 行で文字 1 つが 949、何も変えないが 853。
増分レイアウトなしでは、3,000 行で何を変えても約 88,000(88ms)。

Blitz 自身の段階別タイマー(`log-phase-times`)で、何も変えない resolve の内訳を見ると、
スタイル 0.2〜0.4、損傷の伝播 0.1、箱の構築 約 92、レイアウト 約 575、ほかは 0.1 以下(マイクロ秒、合計 約 670 の回)。

読み取れること。

- **状態の段は増分**: signal の書き込みから文書への書き込みまで 2 マイクロ秒前後で、行数にほぼよらない。
- **スタイルと損傷の伝播も増分**: 1 マイクロ秒未満。
- **`blitz-dom` の増分モードは効いている**: 増分なしの約 45 分の 1。
- **それでも行数に比例する下限が残る**: 何も変えなくても 3,000 行で約 0.7〜0.9ms。内訳はレイアウト段階と箱の構築。
  レイアウト段階のほうは、先の Taffy 単体の計測で見た丸めの全体走査と同じ形をしている(Blitz のコードで丸めを呼ぶ箇所は確認したが、
  この時間が丸めによるものかは切り分けていない)。箱の構築は、ソースに「TODO: make incremental」とある再帰。
- **親が持つ子の数が効く**: 全行を 1 つの親に置くと、変更のたびにその親のレイアウトが全部の子を見る。グループに分けると、変更の上乗せ分はほぼ消える。
- **描画は文書の大きさによらない**: 画面に見える範囲だけを描くので、100 行でも 10,000 行でも約 1ms(CPU レンダラ、800×600)。
  損傷矩形はないので、画面内は毎回全部描く。

### 枠線が消える仕組み(上流の PR #902 の説明と、こちらの再現)

Stylo は枠線の太さを端末のピクセル単位に揃える。倍率 1.5 では、`1px` の枠線は 0.667 CSS ピクセルになってレイアウトに届く。
Taffy の丸め(`round_layout`)は、各辺を位置の累積から CSS ピクセルの整数に丸めて差を取るので、その枠線の両端が同じ整数に落ちると太さが 0 になる。
どの辺が消えるかは位置の端数で決まる。

`blitz-dom` はこの丸めを resolve の中で無条件に、ルートから全ノードに対して呼んでいる(`resolve.rs`)。外から止める口はない。
計測で見た「何も変えなくても行数に比例する下限」のうちレイアウト段階の分は、この呼び出しを含む。

### 外からの補正

丸める前のレイアウトと丸めた後のレイアウトは、どちらもノードから読める(後者は書ける)。
そこで、丸める前には太さがあり、丸めた後に 0 になった辺へ、端末 1 ピクセル分の太さを戻す処理を入れた。

- 置いた場所は 2 つ。ウィンドウなしで使うつなぐ層の `resolve` と、写して持っている blitz-shell の resolve の直後(描画の前)。
  shell が文書の resolve と描画を続けて行うので、ウィンドウでは shell の中に置くしかなかった。
- 倍率 1.25、1.33、1.5、1.67 で、どの行の枠線も 0 でなくなった。倍率 1.5 の画像で、入力欄と全部の行に枠線が出ることを確認した(CPU・GPU とも)。テストを足した。
- 毎回の resolve の後に全ノードを歩くので、下限をさらに増やす。小数の倍率のときだけ動く。
- 上流の PR は丸めそのものを端末ピクセルの格子に合わせる直し方で、こちらの補正より正確。こちらは「0 にされた辺を戻す」だけなので、枠線の位置が最大で端末 1 ピクセルずれる場合がある。

### 当たり判定の原因と、利用側での回避(2026-11-12)

原因は `Node::hit_inner` の判定に 2 つある(上流の #1182 の説明と、こちらで読んだコードが一致)。

1. 点にスクロール量を足して中身の座標に直した後、自分の箱の範囲を「0 〜 スクロール量+大きさ」で見ている。正しくは「スクロール量 〜 スクロール量+大きさ」。
   スクロールした分だけ、箱の上と左まで自分の範囲として受け付ける。
2. 点が自分の箱の外でも、中身の広がりの中なら子を調べる。容器が中身を切り取っているかどうかを見ない。描画は切り取るが、当たり判定は切り取らない。

- この形は v0.1.0 から 0.3.0-beta.4 まで同じ。main では 1 が直っていて、2 はまだ(PR #1324 が open)。
- 上流の報告者は、写して持っている `blitz-dom` を直して対処している。issue に利用側での回避策の記述はない。
- Dioxus の README は Blitz によるレンダラーを「Experimental Native Renderer」としていて、標準のデスクトップ向けの描画は webview。

利用側のスタイルで避けられるかを試した(`src/bin/hit.rs`。バー・高さ 100 のスクロールするリスト(100 行)・フッターを縦に並べ、それぞれをクリック)。

| スタイル | スクロール 0: バー / フッター | スクロール 1000: バー / フッター |
|---|---|---|
| そのまま | 自分 / 自分 | **隠れた行** / 自分 |
| バーとフッターを前面に(`position: relative; z-index: 1`) | 自分 / 自分 | 自分 / 自分 |
| リストを独立した重なりに(`isolation: isolate`) | 自分 / 自分 | **隠れた行** / 自分 |
| リストを位置指定(`position: relative; z-index: 0`) | 自分 / **隠れた行** | **隠れた行** / **隠れた行** |
| リストに `contain: paint` | 自分 / 自分 | **隠れた行** / 自分 |

- 隣の要素を前面に出す指定(2 行目)で、この配置では避けられた。当たり判定が、前面に出した要素を通常の中身より先に調べるため。
- リスト側の指定では避けられなかった。位置指定はむしろ悪化させた。
- 試したのはこの 1 つの配置だけ。隣の要素を前面に出すと重なり順が変わるので、ポップアップなど他の重なりとの兼ね合いは見ていない。
  また、スクロールする領域の隣に置くものすべてに書く必要があり、書き忘れても見た目では分からない。

## 追補 6: ターミナルを独自描画で載せたときの時間(2026-11-12)

ターミナルは文書が記述しない内容なので、ウィジェットが自分で描く(`blitz_dom::Widget::paint` が描画命令の列を返す)。
その 1 フレーム分に当たる仕事を、ウィンドウなしで測った(`src/bin/terminal.rs`)。

|---|---|---:|---:|---:|---:|---:|

| 120×40 | 1(840×720) | 1641 | 37 | 131 | 3187(689) | 9013(202) |
| 120×40 | 1.5(1260×1080) | 1530 | 37 | 135 | 3698(993) | 14244(349) |
| 120×40 | 2(1680×1440) | 1605 | 39 | 147 | 4309(1612) | 13407(1235) |
| 240×70 | 1(1680×1260) | 5358 | 72 | 491 | 6650(1137) | 32292(537) |

読み取れること。

- **GPU なら 1 フレームの枠に収まる**: 120×40 で 3〜4ms、240×70 で 7〜10ms。この値は画像を読み戻す時間を含む(ウィンドウでは読み戻さない)。

- ウィンドウに出したときの実際のフレーム時間(読み戻しなし、垂直同期あり)。
- 今の gpui 版のターミナルが同じ画面を描く時間。比べる数値を持っていない。
- 日本語や絵文字など、幅の違う文字とフォントのフォールバック。リガチャ。
- ウィジェットとして文書に入れたときの上乗せ(文書の描画が、記録された命令列を取り込む分)。

| 整形 | `parley` 0.12 | `LayoutContext::ranged_builder` → `build` → `break_all_lines` |
| 命令の記録 | `anyrender` 0.14 | `PaintScene` の `fill` と `draw_glyphs` を、記録用の `Scene` に対して呼ぶ |

- ウィンドウも、Wayland の面も使っていない。測ったのは、1 画面分の命令を渡してから画像が手元に戻るまでの時間で、表示のスループットではない。
- GPU は AMD Radeon 890M(内蔵、Vulkan、Mesa RADV)が使われていた(`src/bin/adapter.rs`)。

### 文書の中のウィジェットとして(`src/bin/terminal.rs`)

同じ画面を `blitz_dom::Widget` にして、文書のページ全体に置き、`blitz_paint::paint_scene` で描いた。
この経路では、Blitz が毎回ウィジェットの `paint` を呼び、返ってきた命令列を複製して文書の描画に流し直す
(`blitz-paint` の `draw_custom_widget`。ソースに「TODO: eliminate clone」とある)。
ミリ秒、中央値(21 回)。GPU は読み戻しを含む。

| 画面 | 倍率 | 単独で描く(GPU) | 文書の中: 変化なし | 文書の中: 1 行ずつスクロール | 文書の中: 全行が毎回変わる |
|---|---|---:|---:|---:|---:|
| 120×40 | 1.5 | 2.1 | 2.5 | 2.9〜5.0 | 4.8〜5.0 |
| 120×40 | 2 | 3.1 | 3.8〜5.0 | 3.8〜4.0 | 5.5〜5.7 |
| 240×70 | 1.5 | 7.9 | 8.8 | 8.9 | 14.0 |
| 240×70 | 2 | 9.2 | 10.4 | 10.5 | 15.6 |

- 文書を通すことの上乗せは、変化なしで 0.3〜1ms 程度。命令列の複製と流し直しは、この規模では大きくない。
- 全行が毎回変わる場合は、全行の整形(1.5〜5ms)がそのまま乗る。
- 値は 2 回の実行の範囲で書いた。回ごとに 1ms 前後動く。

### 一般的なターミナルの描画方式との比較

ここで試した方式(Vello)と、GPU を使うターミナルで一般的な方式は、文字の描き方が違う。

| | 一般的な GPU ターミナルの方式 | ここで試した方式(Vello 0.11) |
|---|---|---|
| 文字 | グリフを一度ビットマップにしてテクスチャ(アトラス)に置き、以後はその四角形を貼る | グリフの輪郭(パス)を命令として渡し、GPU が毎フレーム塗りつぶす |
| 1 フレームの仕事 | セルごとの位置・グリフ番号・色を並べたバッファを GPU へ送り、少数の描画呼び出しで全セルを描く | 行ごとのグリフ列と矩形を描画命令にし、レンダラが全体をラスタライズする |
| 持ち越すもの | グリフのビットマップ | グリフの輪郭の符号化(`vello_encoding` の `GlyphCache`)。塗りつぶしの結果は持ち越さない |
| 拡大縮小 | 大きさごとにビットマップを作り直す | 輪郭なので作り直さない |

- 今の Horizon(gpui)は前者に当たる。gpui はグリフをアトラスに置き、スプライト(`MonochromeSprite`)として描く(gpui-pre 0.3.11 のソースで確認)。
  Horizon 側は、行ごとに整形結果を世代つきで持ち、背景は四角形、文字は整形済みの行を描いている(`src/terminal/paint.rs`)。
- Alacritty、kitty、WezTerm、Ghostty はグリフアトラスとセル単位の描画を使う、foot は CPU で描いて損傷した範囲だけ更新する、というのは一般に知られている作りで、
  この調査ではソースを確かめていない(2026 年 6 月までの知識による)。
- `vello` 0.11 は README で「GPU compute-centric 2D renderer research」と名乗っている。上流のリポジトリでは、利用者向けのレンダラは別方式(Sparse Strips の `vello_cpu` / `vello_gpu`)に移っている。
  今回 GPU で測ったのは、この研究寄りの計算シェーダ方式のほう。

速さについて言えること、言えないこと。

- アトラス方式は、文字の塗りつぶしを一度しかしないので、1 フレームの仕事はセルの数に比例するバッファの更新が中心になる。原理的には、ここで試した方式より 1 フレームの仕事が少ない。
- ただし、今の Horizon のターミナルが同じ画面を描く時間は測っていない。「どのくらい差があるか」は、数値では言えない。
- この土台でアトラス方式を取ることもできる。ウィジェットは wgpu のテクスチャを自分で持って描き、それを文書に貼る口がある(`Widget::can_create_surfaces` と `paint` の説明)。その場合、ターミナルの描画は Vello を通らない。試してはいない。

### デスクトップで見る

`src/bin/terminal_window.rs` が、同じ画面をウィンドウに出す。画面の 1 行目に、ウィジェットの `paint` にかかった時間と、フレームの間隔(fps)を表示する。
ウィンドウの大きさに合わせてセルの数が変わる。

```sh
cargo run --release --bin terminal_window -- scroll   # 1 行ずつスクロール(既定)
cargo run --release --bin terminal_window -- flood    # 全行が毎回変わる
cargo run --release --bin terminal_window -- still    # 変化なし
```

こちらではウィンドウを開いていないので、表示される数値は未確認。

ウィンドウ版(`terminal_window`)は、オーナーがデスクトップ(GNOME、拡大率 150%)で動かして目視で確認し、問題を感じる点はなかった(2026-11-12)。表示された fps などの数値は記録していない。

### 長い履歴での時間

仮想化はしていない。全ユニットが文書の要素として存在する。
進行中のターンに 4 文字ずつ流し込み、更新 1 回あたりを測った(`cargo run --release --bin agent -- measure`、中央値 / 最悪、ミリ秒)。

| 10 | 22 | 488 | 12.8 | 0.06 / 0.13 | 0.31 / 0.56 | 0.01 | 0.16 / 0.41 |
| 50 | 102 | 2,168 | 18.4 | 0.07 / 0.14 | 0.46 / 0.82 | 0.07 | 0.26 / 0.50 |
| 200 | 402 | 8,468 | 69.7 | 0.12 / 0.21 | 1.34 / 2.10 | 0.39 | 0.73 / 1.07 |

倍率 1.0 では、400 ターンの resolve が 1.88 / 4.02。差の約 1.1 ms は、追補 4 の枠線の補正(全ノードを歩く)の分。

  16 ms の枠には収まるが、上限がない。追補 2 で見た `blitz-dom` の下限(丸めと箱の構築が全体を歩く)が、そのまま出ている。

- gpui 版の同じ操作の時間は測っていない。

### 土台に足す必要があったもの

- **レイアウトの後に動く口**(`each_layout`)。末尾への追従は、伸びた後の高さが分かってからスクロールする。
  `blitz-shell` にはこの口がなく、取り込んだ `blitz-shell` に 1 か所足した(`set_after_resolve`)。変更はこれで 3 か所になった。
- **既定の動作を止める口と、伝播を止める口**(`prevent_default`、`stop_propagation`)。Enter を送信に使い、`Stop` のクリックでレシートを開閉させないため。`blitz-dom` の側に仕組みはあり、つなぐ層が渡していなかった。
- **外からの更新を入れる口**(`App::on_poll`)。`Document::poll` がシェルから呼ばれ、渡される waker で次の呼び出しを起こせる。
- **つなぐ層の不具合を 1 つ直した。** キーつきリストの並びの確認が、項目数の 2 乗の比較をしていた。

### つまずいたこと

- **フォーカス。** `Stop` のようにフォーカスを取れない要素を押すと、入力欄からフォーカスが外れ、Enter と Esc がビューに届かなくなる。Markdown ビューと同じ `blitz-dom` の挙動。押し終わったら入力欄へフォーカスを戻す処理を入れた。

- **ホイールは、ポインタが乗っている要素をスクロールする。** テストでは先にポインタを動かす必要があった。
- **スクロールする要素の `get_client_bounding_rect` は、自分のスクロール量だけずれた値を返す。** 列の下端を、入力欄の位置から求めて避けた。

### 確かめていないもの

- 仮想化(見えている範囲の要素だけを持つ)を、この土台の上で作れるか。
- 履歴の文字の選択とコピー。
- 入力欄のプレースホルダ(追補 3 のとおり表示されない)。
- gpui 版との見た目の一致(色と寸法は固定値で近づけただけ)、テーマと文字サイズへの追従。

## 追補 10: ボード一覧のドラッグ&ドロップと、ビューを収める殻(2026-11-12)

エージェントのペインに続けて、残りの 2 つを同じように書いて確かめた。

### ボード一覧の並べ替え(`src/board.rs`、264 行)

gpui 版(`src/board/list.rs`)は、gpui のドラッグの仕組み(`on_drag`、`on_drag_move`、`on_drop`)を使う。
`blitz-dom` にドラッグの仕組みはないので、ポインタのイベントと当たり判定と行の箱で書いた。
一覧の他の機能(木の折りたたみ、未読、タスクの追加)は移していない。

`tests/board.rs` の 2 件が通る。マウスの移動、押下、押したままの移動、解放のイベントで動かしている。

- 押して少し動かすまでは運ばれない。動かすと、行の写しがポインタについてくる(`pointer-events: none` で、当たり判定を素通しにしている)。
- ポインタが行の上半分か下半分かで、挿入位置の線が行の上か下に出る。離しても何も動かない位置には出ない。
- 離すと、線の位置へ移る。
- クリックで選択し、`j` / `k` で選択が動く。

### ビューを収める殻(`src/workspace.rs`、713 行)

タブ、縦横の分割、境界のドラッグ、ワークスペースモード、コマンドのパレット。
ペインには、ここまでに書いた 4 つ(エージェント、Markdown、ボード、ターミナルの画面)を入れられる。

`tests/workspace.rs` の 5 件が通る。倍率 1.5 でパレットを開いた状態を 1 枚描いて目で確認した。
ウィンドウ(`cargo run --release --bin workspace`)は、こちらでは起動していない。

- **4 つのビューが 1 つの文書に同居する。** それぞれが自分の `.chip` や `.title` を持つが、互いに影響しない。
- **境界をドラッグすると比率が変わる。** 離した後の移動では変わらない。
- **並べ直してもペインの中身が残る。** 分割を変えると、ペインの要素を古い並びから外して新しい並びに入れる。
  入力欄に打った文字、Markdown のスクロール位置、ボードの選択が残ることを見ている。
- **パレット。** `Ctrl+'` でモードに入り、`:` で開く。打つと絞り込まれ、矢印で選び、Enter で実行、Esc で閉じる。項目のクリックでも実行する。
  分割、ペインを閉じる、ペインに出すビューの切り替えを、パレットから実行している。
- **モード中のキーはビューに届かない。** ボードにフォーカスがあるとき `j` は選択を動かすが、モード中は動かさない。
- **タブ。** ラベルのクリックで切り替わり、表示されるのはそのタブのペインだけ。

### 分かったこと

- **スタイルシートは文書全体で 1 つ。** ビューごとに書いた CSS を並べると、同じクラス名が衝突する。
  各ビューのルールを、そのビューのルート要素のクラスの下に入れ子で書いて閉じ込めた(CSS の入れ子は `blitz-dom` で効く)。
  `@keyframes` の名前は閉じ込められない。
- **キーの配送にキャプチャの段階がない。** キーはフォーカスのある要素から外側へ伝わるので、殻がビューより先にキーを取ることができない。
  モードに入るときにフォーカスを殻自身へ移して、ビューを経由しないようにした。
  `Ctrl+'` 自体はビューを先に通る(ビューが無視する前提)。
- **フォーカスを取れない要素を押すと、ページ自体にフォーカスが移る。** 3 つのビューで同じ問題になったので、ビューごとの対処をやめ、つなぐ層で「押された位置の祖先のうち `tabindex` を持つ最も近い要素」へ移すようにした(ブラウザの挙動)。
- **ビューは、作られるときに自分でフォーカスを取ってはいけない。** 複数を並べると、最後に作られたものが取る。置く側が決めるようにした。
- **文書を書き換えた後、次のレイアウトまでの間は、箱を読めない。** 2 つの形で踏んだ。
  - `blitz-dom` の `set_focus_to` は、ノードのページ上の位置を求めるために親の箱を辿る。親が作り直された直後だと、消えたノードを指していてパニックする。
    フォーカスの移動を、次のレイアウトの後に行うようにした。その間に届いたキーは、前のフォーカス先へ行く。
  - 入力メソッドの候補位置の更新(追補 3)も同じ経路を通っていた。レイアウトの後に移した。

  これに合わせて、ハンドラが文書に頼む仕事を 2 つに分けた: レイアウトを読むもの(イベントの直後、書き換えの前)と、書き換えの結果に作用するもの(書き換えの後)。
- **`display: none` の下のノードは、`get_client_bounding_rect` が古い箱を返す。** 表示されているかは、当たり判定で確かめた。

### 土台に足したもの(`src/lib.rs`、705 行)

## 追補 11: 長い一覧を、見えている範囲だけ要素にする(2026-11-12)

追補 9 で、エージェントのペインは履歴の長さに比例して更新が遅くなった。
見えている範囲のユニットだけを文書に持つ形(gpui の `list` がしていること)を、この土台の上で作れるかを確かめた。作れた。

### 作ったもの(`spikes/ui-foundation/src/windowed.rs`、約 250 行)

スクロールする箱の中に、上の空白、ある範囲の項目、下の空白を置く。

1. レイアウトのたびに、要素になっている項目の高さを読んで覚える。
2. 空白の高さを、それが代わりをしている項目の高さの合計にする。一度も要素になっていない項目は、測った高さの平均で見積もる。
3. スクロール位置から、要素にする範囲を決め直す(箱の上下に 600 px の余裕を持たせる)。変わったら、一覧を組み直して、描く前にもう一度レイアウトする。
4. 初めて要素になった項目は、見積もりと高さが違う。見えているものが跳ねないよう、見えている項目の 1 つを画面上の同じ位置に保つ(その項目が動いた分だけスクロールする)。
5. 末尾への追従は、この中で行う。

エージェントのペインは既定でこれを使う。比べるために、全ユニットを要素にする形も残した(`Column::Whole`)。

### 確かめたこと

`tests/agent.rs` に 1 件足し、全部で 22 件が通る。足したテストは、200 ターン(400 ユニット、ターンごとに高さが違う)の履歴で次を見ている。

- 開いたとき、要素になっているユニットは 40 未満。
- 末尾から先頭まで、ホイール 400 px ずつで上る。各段で、見えているユニットは 400 px(誤差 1 px 未満)だけ動き、段が終わった後は動かない。要素の数は 40 未満のまま。
- 先頭に着くと、最初のユニットが列の上端にある。
- 先頭でレシートを開き、末尾へ行って戻ると、開いたまま(要素は間で捨てられ、作り直されている)。

追補 9 の 6 件も、この形で通る。スクロール位置の数値そのものを比べていたテストは、ユニットの画面上の位置を比べるように直した(上のユニットが見積もりから実際の高さに変わると、見た目は動かずにスクロール位置の数値だけが動くため)。

### 時間

### 土台に足す必要があったもの

## 追補 12: ターミナルの実物(2026-11-12)

追補 6 と 7 で確かめたのは、画面の描画の時間だけだった。
実際のシェルを動かし、キー、入力メソッド、貼り付け、マウス、リサイズを通した。

### 作ったもの

- `spikes/ui-foundation/src/pty.rs`(約 220 行): PTY を開いてシェルを起動し、Horizon のターミナルのコア(`horizon-terminal-core` の `run_terminal_core`)をそのまま動かす。
  Horizon では `horizon-terminald` が持つ部分(`crates/horizon-terminald/src/terminal.rs`)を、同じスレッドの組み方で試作のプロセスの中に置いた。ソケット越しの接続はしていない。
- `spikes/ui-foundation/src/terminal.rs`(約 760 行): ビュー。文書のイベントをコアのコマンド(`TerminalCommand`)に変え、コアのフレーム(`TerminalFrame`)を独自描画のウィジェットで描く。

コアには手を入れていない。エミュレーション、キーの符号化、選択、スクロールバックはコアの仕事で、ビューはそれを呼ぶだけ。

### 確かめたこと

`tests/terminal.rs` の 7 件が通る(全体で 29 件)。どれも実際の `sh` を PTY で動かし、画面に出た文字で判定している。

- **キー入力。** Shift つきの記号を含むコマンドを 1 キーずつ打って実行できる。Ctrl+C で `cat` が止まり、シェルに戻る。Backspace が効き、矢印キーはエスケープシーケンスとして届く。
- **入力メソッド。** 未確定の文字はビューが持ち、シェルには送られない。未確定の間のキーはシェルへ行かない。確定した文字が送られる。
- **貼り付け。** 貼り付けたコマンドが実行される。
- **リサイズ。** 箱の大きさから桁数と行数を出して伝え、`stty size` がその値を返す。箱を縮めると新しい値を返す。
- **選択とコピー。** ドラッグしたセルの範囲がフレームの選択になり、Ctrl+Shift+C でその文字がクリップボード行きとして返る。
- **スクロールバック。** `seq 1 200` の後、ホイールで流れた行に戻れ、戻すと末尾に戻る。
- **終了。** `exit` でシェルが終わったことをビューが知る。

倍率 1.5 で 1 枚描いて目で確認した(`cargo run --release --bin live_terminal -- picture out.png`)。
全角と半角が混ざった行で、行末の `|` が同じ桁に揃う。16 色、256 色、24 ビット色、背景色が出る。
ウィンドウ(`cargo run --release --bin live_terminal`)は、こちらでは起動していない。

### 長い出力

`cargo run --release --bin live_terminal -- measure`(142 桁 × 33 行、倍率 1.5、GPU で描いて読み戻し)。

| コマンド | 終わるまで | 描いたフレーム | 1 フレームの描画と読み戻し(中央値) |
|---|---|---|---|
| `seq 1 200000` | 0.10 秒 | 26 | 2.47 ms |
| `yes '…日本語' \| head -n 200000` | 0.13 秒 | 56 | 1.85 ms |

コアがフレームを 16 ms ごとにまとめるので、出力の量に対して描く回数は少ない。行は、前に描いた行と違うときだけ整形し直している。

### 土台の側で必要だったこと

- **入力メソッドは、`blitz-dom` 自身の入力欄にフォーカスがあるときしか有効にならない。** 入力欄でない要素が文字を受けるための口をつなぐ層に足した(`takes_text`)。フォーカスがある間、シェルに入力メソッドを有効にさせ、候補の位置としてカーソルのセルを伝える。未確定の文字は `composition` イベントで届く。
- **貼り付けも、`blitz-dom` 自身の入力欄にしか届かない。** つなぐ層で受けて、登録した要素へ渡すようにした(`on_paste`)。
- **コードからフォーカスを移したとき、`focus` イベントは出ない。** フォーカスの有無は、レイアウトのたびに文書に尋ねている。
- **グリフをセルの位置に置く。** 行を Parley で整形したままの位置で描くと、全角の文字の幅がセル 2 つ分とは限らず、後ろがずれる。
  整形の結果を文字のかたまりごとに取り出し、それぞれを自分の桁の位置に描いている。

### 分かったこと

- **ターミナルのコアは、UI の土台と無関係に使える。** `run_terminal_core` の入口(バイト列、コマンド、フレーム)だけで足りた。
- **追補 10 の「キャプチャの段階がない」が、ここで効く。** ターミナルにフォーカスがあると、`Ctrl+'` は殻より先にターミナルに届き、シェルへ送られる。殻のキーを先に取る仕組みが要る。今は入れていない。
- **既定の色の反転文字で、前景と背景が同じ色のフレームが来る。** `printf '\033[7minverse\033[0m'` のフレームは、前景も背景も `Foreground` だった(`crates/horizon-terminal-core/src/core/render.rs` の `cell_bg` は背景だけを入れ替えている)。
  描いた 1 枚では、黒い箱になって文字が見えない。gpui 版の描画(`src/terminal/shaping.rs`)も前景をそのまま色にしているように読めるが、現行の Horizon での見え方は確かめていない。この試作の土台とは関係のない観察。

- Horizon のスクロールバックの設計(履歴の窓を取り寄せる形、`src/terminal/scrollback.rs`)。ここではコアの表示位置を動かす単純な形を使った。
- 下線、斜体、取り消し線、リンク、太字の字体、カーソルの点滅、ベル、タイトル、OSC での色の上書き、テーマ。
