# コードデータベース:Go の索引と units(2026-10-30)

コードデータベース(`duckdb-ext/`、`docs/code-database-design.md`)に Go を足した。オーナーは 2026-10-30 に範囲を次のように選んだ:索引と units まで(モジュールの規則や複雑度は次の段)、言語の知識は `lang/<language>.sql` に分ける、検証は fixture で行い、実在の Go リポジトリでの読み合わせはコードの公開範囲の都合で別のアカウントのセッションに渡すプロンプトにする、macOS での実行も含める。

## 1. scip-go 0.2.7 の出力(測ったこと)

小さな Go モジュール(パッケージ 2 つ、テストファイル、ジェネリクス、`const`/`var`/`type` のグループ、interface、メソッド)を `scip-go index` にかけ、`scip-probe` で行を読んだ。

- **種別。** `Function`、`Method`、`MethodSpecification`(interface のメソッド)、`Type`(`type Kind int`)、`Struct`、`Interface`、`TypeAlias`、`Field`、`Constant`、`Variable`、`Package`。関数の中の名前、引数、レシーバ、型引数は `local N`。
- **範囲。** `enclosing_range` があるのは関数とメソッドだけで、`func` から閉じ括弧までである(doc コメントは含まない)。型、定数、変数、interface のメソッド、パッケージには範囲がない。rust-analyzer がすべての定義に範囲を付け、ファイルのモジュールに全体の範囲を付けるのと違う。
- **パッケージ。** パッケージの symbol(`…\`example.com/m/shapes\`/`)は、各ファイルの `package` 節で定義される(ファイルごとに 1 つの定義の出現)。シンボル情報は 1 つの文書の下にだけ載る(3 ファイルのパッケージで 1 件)ので、(文書, symbol)で引くと他のファイルのパッケージが落ちる。doc コメントはパッケージ単位で 1 つにまとめられる。
- **パッケージ名。** symbol の package は Go モジュールのパス(`example.com/m`)、version は git リポジトリの中ではコミットの短いハッシュ、外では `.`。
- **テストの main。** `go test` が生成する main パッケージの文書が、ビルドキャッシュ(`~/Library/Caches/go-build/…`)への相対パスで索引に入る。リポジトリのファイルと一致しないので `file_id` が NULL になり、unit にはならない。
- **署名。** `signature_documentation` は `func Describe(s Shape, label string) string`、`func (*List[T]).Push(v T, more ...T)`、`func (Shape).Area() float64` の形で、引数の名前を含む。

## 2. Go の units の対応づけ

`lang/go.sql` の `go_units`。列の意味は Rust と同じ(`views/units.sql` の見出し)で、Go での読みを次のように決めた。

- **種別。** Function → function、Method と MethodSpecification → method、Type・Struct・Interface・TypeAlias → type、Package → module、Constant とローカルでない Variable(パッケージの `var`)→ constant。Field は unit にしない(Rust の構造体のフィールドと同じ)。
- **範囲。** 関数とメソッドは SCIP の範囲。ほかは sitting_duck の構文木から取る:名前を宣言する spec(`type_spec`、`type_alias`、`const_spec`、`var_spec`)、その宣言が spec を 1 つしか持たないときは宣言全体(`type X struct {…}` を `type` から)。`const a, b = 1, 2` のように 1 つの spec が宣言する名前は範囲を共有する(兄弟になる)。interface のメソッドは `method_elem`。doc コメントは関数と同じく範囲に入れない(Rust は rust-analyzer に従って含む。`loc` の言語間の比較ではこの差が残る)。
- **ファイルのモジュール。** 各ファイルの `package` 節の定義の出現を 1 つの unit とし、範囲はファイルの構文木の根(`source_file`)全体。`coupling` が crate の `loc` をファイルのモジュールの `loc` の和で出すので、全体の範囲が要る。
- **impl。** Go に impl ブロックはない。メソッドは `member_of = 'impl'`、`impl_key` はレシーバの型の symbol(メソッドの symbol から最後の記述子を除いたもの)、`impl_type` はその型名とした。1 つの型のメソッドがファイルをまたいでも同じ鍵になる。`impl_header_line` と `impl_trait` は NULL。interface のメソッドは `member_of = 'trait'`。
- **名前。** `crate` は Go モジュール、`qualified_name` はパッケージより下の記述子(`Circle.Area`、`Shape.Area`)。シンボル情報は symbol だけで引く(1 節)。
- **可視性。** 名前の最初の文字が大文字(`\p{Lu}`)なら `pub`、そうでなければ `private`。Go の非公開はパッケージ内で、Rust の `private`(モジュール内)より広いが、語彙は増やしていない。interface のメソッドとファイルのモジュールは NULL。
- **引数。** 署名の、関数では深さ 0 の最初の括弧、メソッドでは 2 番目(レシーバの次)の括弧の中のカンマで数える。`a, b int` は 2。Rust が `self` を数えるのに合わせてレシーバを 1 と数える。
- **テスト。** ファイルが `*_test.go` か `extra_test_paths` に一致する unit。`extra_test_attributes` は Go では意味を持たない。

## 3. 言語の分離

Rust の知識(種別の対応、impl の記述子、テストの規則、署名の数え方、`impl_base_name` などのマクロ)を `views/units.sql` から `lang/rust.sql` の `rust_units` に移した。`views/units.sql` の `derived_units` は `rust_units` と `go_units` の和をとり、どの言語でも同じこと(`unit_id` の番号、`parent_unit_id`、`loc`、テストの中にある unit へ `is_test` を広げること)だけを行う。各言語のビューは自分の言語のファイル(`files.language`)だけを読み、言語の規則が自分で決めるテストを `test_by_rule` として渡す。`languages` の既定値は `MAP {'rs': 'rust', 'go': 'go'}` になった。

**等価性の確認。** 分ける前(HEAD の SQL)と後で、同じ SCIP 索引から作った 20 の層(`units`、`unit_occurrences`、`symbol_units`、`unit_references`、`unit_edges`、`unit_ancestors`、`impls`、`impl_targets`、`unit_impl_type`、`modules`、`unit_module`、`module_edges`、`crate_edges`、`unit_scope`、`unit_fan_in`、`unit_fan_out`、`unit_reference_status`、`unit_debt_markers`、`unit_complexity`、`unit_quality`)を Parquet に書き、`EXCEPT ALL` を両方向にとった。rust-analyzer 1.99.1 で、`duckdb-ext/` のワークスペース(252 units)と Horizon のルートのワークスペース(8,718 units、29 万 2,780 の出現)のどちらも、全層で差が 0 行だった。

**費用。** sitting_duck の `read_ast` はファイル名のフィルタを押し下げず、渡されたファイルをすべて解析する。`go_units` が `file_ast` を読むと、Go のファイルがないリポジトリでも全ファイルを解析し、live での `units` が 0.14 s から 0.6 s になった(Horizon のルート)。Go の構文木は `go_file_ast` が読み、`read_ast` に Go のファイルのパスだけを渡す(空のリストを避けるため存在しないパスを 1 つ足し、`ignore_errors` で飛ばす)。これで 0.17 s になった。`refresh.sql` は `go_file_ast` を、内容 id ごとに保つ構文木の表に向け直す。

## 4. `code-db index`

追跡されている `go.mod` があり、`.go` のソースファイルを持つディレクトリを Go モジュールとし、それぞれで `scip-go index --quiet --output …` を走らせる(`SCIP_GO`、既定は PATH の `scip-go`)。索引の名前はルートが `go.scip`、ほかは `go-<パスの / を + にしたもの>.scip`。入れ子のモジュールは別のモジュールで、外側の `./...` には入らない(Go の規則)。`go.work` は読まない。rust-analyzer と scip-go は、索引にするものがあるときだけ要る(Go だけのリポジトリで rust-analyzer がなくても動く)。jscpd は `--format rust,go` にした。

## 5. macOS

- `build.sh` は `uname` からプラットフォーム(`linux_amd64`、`linux_arm64`、`osx_arm64`、`osx_amd64`)とライブラリの拡張子(`.so`、`.dylib`)を決め、`target/extension/v2.0.0/<platform>/` に書いて、`host` をそこへのリンクにする。`LOAD` はリテラルしかとらないので、`00_load.sql`、`code-db`、host check は `host` から読む。
- Homebrew の `duckdb` は 2.0.0 で、CLI と `libduckdb.dylib` を兼ねる。`DUCKDB_LIB_DIR=/opt/homebrew/lib` でビルドでき、install name が絶対パスなので rpath は要らない。拡張(フッターは `osx_arm64`)は Homebrew の CLI と `duckdb` クレートで読み込めた。
- `scripts/fetch-scip-cli.sh` はプラットフォームごとのアーカイブと sha256(リリースのアセットのダイジェスト。linux-amd64 は従来のピンと一致した)を持ち、BSD の `sha256sum` は `-c` の扱いが違うので、ハッシュを計算して比べる。
- `/proc/meminfo` がないので、メモリの上限は DuckDB の既定の 60%(既存のフォールバック)、外部ツールの上限は付かない(systemd-run も prlimit もない。`code-db` が警告する)。
- `duckdb-ext/check.sh` は macOS(arm64)で通った。stable の rust-analyzer 1.99.1 を PATH に置く必要があった(この機械の既定の nightly には rust-analyzer がなかった)。`check.py` は uv がなく走らせていない。

## 6. 検証

- `code-db` の end-to-end テストに Go の fixture を足した(`go_modules_index_and_units`):モジュール 2 つ(ルートと `tools/gen`)、パッケージ 2 つ、テストファイル、interface、値と pointer のレシーバ、`const` のグループ。索引が `go.scip` と `go-tools+gen.scip` の 2 つになること、rust-analyzer なしで動くこと、jscpd に `.go` が渡ること、全 unit の行(パス、crate、種別、名前、範囲、テスト、可視性、引数、impl)、ファイルとパッケージをまたぐ unit の辺を確かめる。scip-go がなければ飛ばす。
- Rust の既存のテスト(`index_settings_and_queries` と単体テスト)はそのまま通った。

## 7. 残り

- **モジュール。** `modules` はファイルのモジュールの規則が Rust のもので、Go のファイルはパス(`shapes/shapes.go`)のモジュールになる。Go のモジュールの単位はパッケージ(ディレクトリ)で、`module_graph`、`module_cycles`、`layer_violations` の Go での読みはこれを決めてから。
- **複雑度。** `unit_complexity` は tree-sitter-rust のノード型(`if_expression` など)を数え、Go の unit はすべて 0 になる。Go のノード型(`if_statement`、`for_statement`、`expression_switch_statement` など)の対応が要る。
- **関係。** scip-go は implementations の relationship を書くが、読むものはない。interface 経由の呼び出しは interface のメソッドに解決されるので、具体型のメソッドが `unreferenced` に出やすい。`main` と `init` もランタイムが呼ぶので参照がない。
- **impl の型の解決。** `impl_targets` は名前で型を引く(Rust の impl の見出し行の参照、同じファイル、同じ crate の順)。Go では `impl_key` が型の symbol そのものなので正確に引けるが、まだそうしていない。同じモジュールの別のパッケージに同名の型があると解決できない。
- **実在のリポジトリ。** fixture でしか確かめていない。実在の Go リポジトリでの読み合わせは別のセッションに渡す。
