# libghostty-vt を端末エンジンにする試作(2026-11-19)

`horizon-terminal-core` の `TerminalCore` の中身を、`alacritty_terminal` から libghostty-vt 1.0.1 に差し替えて、既存のテストをそのまま走らせた記録。
試作はブランチ `worktree-ghostty-vt-spike` にあり、main には入れない。

この文書は事実の記録で、移行するかどうかの判断は含まない。

## 何をしたか

- 依存を `alacritty_terminal` 0.26.0 から `libghostty-vt`(uzaaft/libghostty-rs のコミット 483ea3d5、`build.rs` が ghostty の vt-1.0.1 を指す)に替えた。
- `TerminalCore` の公開関数(23 個)の形は変えず、中身を書き直した。対象は `core.rs`、`core/render.rs`、`core/events.rs`、`core/color.rs`。
- 通知とプログラム状態の取り出し(`core/osc_notify.rs`、`core/program_status.rs`)と、キーのエンコーダ(`protocol/kitty_keyboard.rs`)は、そのまま残した。
- ワイヤ、セッションのループ、デーモン、ビューは変えていない。

書き直した 4 ファイルは合計約 1500 行(差し替え前は約 1600 行)。

## 既存のテストの結果

テストは変更していない。例外は 2 行で、セッションのループのテストが古いエンジンの色の型(`alacritty_terminal::vte::ansi::Rgb`)を名指ししていた箇所を、クレート自身の型に替えた。

| 範囲 | 件数 | 通過 | 失敗 |
|---|---:|---:|---:|
| `horizon-terminal-core` | 154 | 151 | 3 |
| ワークスペース全体(拡張をビルドした状態) | 2386 | 2383 | 3(同じ 3 件) |

ワークスペース全体には、実際のシェルを PTY で動かすテスト(`tests/terminal.rs`、`tests/terminald.rs`、`tests/workspace.rs`、`horizon-terminald` の e2e)が含まれる。

### 失敗した 3 件

- **`da1_query_reports_primary_device_attributes`**: 端末の種類の問い合わせ(`CSI c`)への応答が違う。テストの期待は `ESC[?6c`、エンジンの応答は `ESC[?62;22c`。エンジンには応答の内容を指定するコールバック(`on_device_attributes`)があり、試作では設定していない。
- **`da2_query_reports_secondary_device_attributes`**: 同じく `CSI > c` への応答が違う。
- **`decrqm_2026_reports_set_while_a_synchronized_update_window_is_open`**: 同期更新の最中に送った問い合わせの応答が、「同期更新が終わるまで出てこない」ことを確かめるテスト。これは `alacritty_terminal` が同期更新中のバイト列をまるごと溜めることから来る挙動で、新しいエンジンはその場で応答する。

### 最初は落ちて、試作の側を直して通したもの

- **履歴が足りない(3 件)**: エンジンの履歴の上限は、既定ではバイト数で約 1 ページ分。行数だけを指定しても、バイト数の上限が先に効いていた。バイト数の上限を外した。
- **同期更新中の画面(2 件)**: `alacritty_terminal` は同期更新の間のバイト列を溜めて、画面には反映しない。新しいエンジンは画面にそのまま書き込み、「保留が始まった・終わった」をコールバックで知らせる。保留が始まった時点のフレームを取っておき、保留の間はそれを返すようにした。保留を時間切れで解く時計は、エンジンが持たないので、こちらで持つ(150ms、`alacritty_terminal` と同じ値にした)。
- **行単位の選択の末尾(1 件)**: `alacritty_terminal` は行単位で選択した文字列の末尾に改行を付ける。エンジンは付けないので、こちらで足した。

## エンジンがやったこと、やらなかったこと

### やったこと(自前の処理が要らなくなった)

- 色の問い合わせ(OSC 4/10/11/12)への応答。既定の色をエンジンに設定しておけば、エンジンが応答する。自前の解決表(`core/color.rs` の後半、約 130 行)が消えた。
- 画面サイズの問い合わせ(`CSI 14 t` など)への応答。サイズを返すコールバックを 1 つ書くだけになった。
- 同期更新中の問い合わせ(DECRQM 2026)への応答の書き換え。`alacritty_terminal` が常に「未設定」と答える癖を直す処理が要らなくなった。
- スクロールしても同じ場所を指し続ける位置。選択の始点をこれで持つようにした。

### やらなかったこと(自前に残った)

- **色の語彙の変換**: エンジンは、パレットの色を番号だけで持つ。`SGR 31`(名前のある赤)と `SGR 38;5;1`(番号 1)を区別しない。Horizon のフレームは両者を別の値(`Named(Red)` と `Indexed(1)`)で送っていたので、試作では番号 0〜15 をすべて名前のある色として送っている。
- **太字・薄字と色の関係**: Horizon のフレームは、太字を「明るい色」、薄字を「暗い色」として色に畳み込んでいる。エンジンは太字と薄字を属性として持つので、畳み込みを自前で行っている。上の点とあわせて、`SGR 38;5;1` に太字を重ねた場合の色が、差し替え前と変わる。
- **反転**: 前景と背景の入れ替えも、フレームの語彙に合わせて自前で行っている。
- **セルをスパンにまとめる処理**: 差し替え前と同じものを使っている。
- **マウス報告と、代替画面でホイールを矢印キーにする処理**: 試作では自前のもの(`core/input.rs`)をそのまま使った。エンジンのマウスエンコーダは試していない。
- **単語・行単位の選択をドラッグで広げる処理**: エンジンの「単語を選ぶ」「行を選ぶ」を両端に当てて、自前でつないでいる。

## キーのエンコーダの突き合わせ

Horizon 自前のエンコーダと、エンジンのエンコーダに、同じ入力を与えて出力を比べた(`core/engine_keys.rs` の `the_engine_s_key_encoder_beside_horizon_s`)。
どちらが正しいかの検査ではなく、一致する数の集計。

- キー 28 種(英字、数字、記号、Enter、Tab、Backspace、Escape、矢印、Home/End、PageUp/Down、Delete、Insert、F1/F5/F12)
- 修飾 8 通り、動作 3 通り(押す、繰り返し、離す)
- プログラムが頼むモード 7 通り

| モード | 一致 / 全体 |
|---|---:|
| 従来形式 | 560 / 672 |
| 従来形式、アプリケーションカーソルキー | 560 / 672 |
| kitty フラグ 1(曖昧さの解消) | 512 / 672 |
| kitty フラグ 3(+ 動作の種類) | 321 / 672 |
| kitty フラグ 7(+ 代替キー) | 321 / 672 |
| kitty フラグ 15(+ 全キーをエスケープコードで) | 534 / 672 |
| kitty フラグ 31(+ 対応する文字) | 523 / 672 |
| 合計 | 3331 / 4704(71%) |

違いの例。

- 従来形式で Ctrl+Alt+a: Horizon は `^A`、エンジンは `ESC ^A`。
- 従来形式で Ctrl+Shift+a: Horizon は `^A`、エンジンは何も出さない。
- フラグ 1 で Ctrl+a: Horizon は `^A`、エンジンは `ESC[97;5u`。
- フラグ 3 で a を離す: Horizon は何も出さない、エンジンは `ESC[97;1:3u`。
- フラグ 15 で Shift+Ctrl+a: Horizon は `ESC[97:65;6u`、エンジンは `ESC[97;6u`。
- フラグ 31 で a: Horizon は `ESC[97;1;97u`、エンジンは `ESC[97;;97u`。

この違いには 3 種類が混ざっていて、切り分けていない。

- 突き合わせの入力の作り方によるもの。エンジンのエンコーダは、プラットフォームのキーイベントに近い入力(物理キー、押されている修飾、文字を作るのに使われた修飾、できた文字、シフトなしの文字)を取る。Horizon のワイヤが運ぶのは termwiz のキーと修飾と文字で、「文字を作るのに使われた修飾」がない。試作では Shift についてだけ補った。
- 仕様の読み方の違い。どちらが kitty の仕様に沿うかは、確かめていない。
- どちらかの不具合。

エンジンのエンコーダに替えるには、ビューが送るキーの情報を増やす(ワイヤの語彙の変更)ことと、違いの 1 つずつを仕様か実物に照らすことが要る。

## 所要時間

同じ計測用テスト(`how_long_a_frame_takes_to_read_out_of_the_engine`)を、両方のエンジンで動かした。
画面は全セルに文字があり、7 セルごとに色が変わる。画面 4 枚分を書き込んでから、フレームと履歴の窓を 41 回ずつ取り出した中央値。

### 書き込み

| | `alacritty_terminal` | libghostty-vt | libghostty-vt、エンジンだけ最適化 |
|---|---:|---:|---:|
| 120×40、34KB、release | 1.61 ms | 0.23〜0.28 ms | — |
| 240×70、117KB、release | 3.23 ms | 0.68〜0.96 ms | — |
| 120×40、34KB、debug | 4.1 ms | 299 ms | 0.65 ms |
| 240×70、117KB、debug | 8.3 ms | 926 ms | 2.4 ms |

- release では、新しいエンジンが 3〜7 倍速い。
- **debug では、そのままだと 70〜110 倍遅い。** バインディングが、Cargo のプロファイルに合わせて Zig の最適化の段階を選ぶため。
- **環境変数 `LIBGHOSTTY_VT_SYS_OPTIMIZE=ReleaseFast` を付けてビルドすると、debug でも今のエンジンより速くなった。** エンジンのビルドし直しに約 70 秒かかった。この環境変数は Cargo が実行される環境に要るので、置き場所は `~/.cargo/config.toml` の `[env]`(DuckDB の設定と同じ場所)になる。

### フレームの取り出し

読み方を 2 通り試した。

- **位置の参照で 1 セルずつ読む**: 最初の形。バインディングの文書は、この読み方を「描画のループの中心に使うものではない」としている。
- **描画用の状態で読む**: 行と、行ごとの変更の印をまとめて渡す API。前のフレームの行を取っておき、エンジンが変更の印を付けた行だけを読み直す。

release、中央値。

| | `alacritty_terminal` | 1 セルずつ | 描画用の状態:変化なし | 1 行だけ変化 | 全行が変化 |
|---|---:|---:|---:|---:|---:|
| 120×40 | 0.13 ms | 0.34 ms | 0.03 ms | 0.04 ms | 0.33 ms |
| 240×70 | 0.43 ms | 1.16 ms | 0.08 ms | 0.10 ms | 1.17 ms |

- `alacritty_terminal` での今の実装は、毎回全行を作り直す。変化の量で時間は変わらない。
- 描画用の状態では、**変化が 1 行なら今の 3〜4 倍速く、全行が変わると今の 2.7 倍遅い。**
- 全行を読むときの遅さは、読み方を替えても変わらなかった。セルごとに、セルの中身、文字、スタイルを別々の呼び出しで取り、スタイルを Horizon の語彙に変換している。まとめて取る API(`get_multi`)や、同じスタイルの使い回しは試していない。
- 「変化なし」の時間には、取っておいた行の複製と、色の上書きの比較(パレット 256 色)が入っている。

### 履歴の窓

位置の参照で 1 セルずつ読む形のまま(描画用の状態は、表示位置とその前後しか持たない)。

| | `alacritty_terminal` | libghostty-vt |
|---|---:|---:|
| 120×40、104 行、release | 0.32 ms | 0.85〜1.3 ms |
| 240×70、134 行、release | 0.89 ms | 2.3〜3.0 ms |

## ビルド

- 追加の設定なしで、ワークスペース全体のビルドとテストが通った。`zig` は proto で入れた 0.17.1。
- バインディングの `build.rs` は、プロファイルごとに ghostty のソースを取得してビルドする。この worktree の `target/` には、debug 用(729MB)と release 用(568MB)の 2 組ができた。
- 使い捨てのプロジェクトで単独に測ったときは、取得とビルドを合わせて 2 分 17 秒だった(debug、初回)。
- worktree の種まき(主チェックアウトの `target/` の写し)が、エンジンのビルド成果物を引き継ぐかは確かめていない。主チェックアウトにはまだ成果物がない。

## スレッド

バインディングの `Terminal` は、別のスレッドへ渡せない型(`Rc` と生ポインタを持つ)。
`TerminalCore` もそうなったが、ワークスペース全体がそのままビルドできた。セッションのループが、自分のスレッドの中で `TerminalCore` を作って使っているため。

## 確かめていないこと

- 実際の窓での動作と体感。
- フレームの全行を読むときの時間を縮める手段(まとめて取る API、スタイルの使い回し)。
- 変更の印に頼ることの正しさ。既存のテストは通ったが、印の付き方そのものを確かめるテストは書いていない。
- 履歴が上限に達したときの振る舞い。エンジンはページ単位でしか捨てないので、指定した行数より多く残る。
- 折り返しの変わるリサイズで、履歴と選択がどうなるか。
- 絵文字や結合文字を含む行の、セルの幅の数え方の違い。
- エンジンのマウスエンコーダ、通知、プログラム状態のコールバックに替えたときの、既存のテストの結果。
- macOS でのビルド。
- あらかじめビルドしたライブラリを pkg-config 経由でリンクする形。

## 追記: デーモンはバイト列を流し、ビューも同じエンジンを持つ形

描画用の状態(行の番号と変更の印)は、同じプロセスの端末からしか作れない。
デーモンの側で作ったそれをビューへ運ぶ口はエンジンに無いので、ビューにも端末を
持たせ、デーモンは PTY のバイト列をそのまま流す形を、この試作の上に通しで組んだ。

### 流れ

デーモンからビューへは、既存の events の経路(順序が保たれ、取りこぼさない)に
3 種類を足した(`TerminalUpdate`)。

- `State { bytes, more }`: 端末の状態(エンジンのスナップショット)。1MB ごとに切る。
- `Output(bytes)`: PTY が書いたバイト列。デーモンの端末が受け取ったものと同じ。
- `Resized(size)`: リサイズ。デーモンの端末に適用した位置に入る。

ビューからデーモンへは 2 種類を足した(`TerminalCommand`)。

- `WantState`: 状態と、その後のバイト列を求める。
- `OutputTaken(n)`: `Output` を n バイト取り込んだ。

デーモンは、送って確認されていないバイト数を数える。2MB を超えたら送るのを止め、
ビューが全部取り込んだと言ってきたところで、状態の「画面の部分」(スナップショットを
画面の終わりで切ったもの)を送り直す。止めていた間のバイト列は送らない。

### ビューの側

`src/terminal/session.rs` の `Session` が、デーモンと同じ `TerminalCore` を持つ。
`src/terminal/mod.rs` は変えていない。

- 描くフレームは手元の端末から読む。
- キー、文字、貼り付け、マウス報告、フォーカス、プログラム宛てのホイールは、手元の
  端末でバイト列にして `Input` で送る。
- 選択、コピー、履歴のスクロール、履歴の窓は手元の端末だけで済み、デーモンへは
  何も送らない。
- リサイズと配色はデーモンへ送る。
- 応答、ベル、タイトル、通知、クリップボードへの書き込み(OSC 52)は今までどおり
  デーモンの端末から出る。手元の端末が出すものは捨てる。

デーモンの既存のフレームの経路は残してある。状態が届くまではそれを描く。

状態が届く前にビューが受けたキーなどは、デーモンへ送らずに溜め、状態が届いてから
手元の端末で順に処理する。最初はデーモンの端末に処理させていたが、その経路
(デーモンがエンコードして PTY へ書く)と、状態が届いた後の経路(ビューがバイト列に
して送る)は別々に PTY へ届くので、切り替わりの瞬間に後のキーが先のキーを追い越した
(`block_art_has_no_seams_in_either_pane_of_a_split_at_a_fractional_scale` が
半分ほどの割合で落ち、打った文字の順序が入れ替わっていた)。

### 表示していないセッション

手元の端末を持つのは、ターミナルのビューが表示中のタブにある間だけにした。

- ビューが作られたとき、`Session::show` が `WantState` を送る。
- タブを切り替えると、シェル(`src/workspace/arrangement.rs`)が、表示中のタブに
  無いターミナルへそれを伝える。そのビューは `Session::hide` を呼び、手元の端末を
  捨て、`StopState`(足したコマンド)を送る。デーモンは以後その流れを送らない。
- タブへ戻ると `WantState` を送り直し、その時点の状態を受け取る。離れていた間の
  出力は、状態の中に入っている
  (`a_terminal_off_the_page_has_no_terminal_of_its_own_until_it_is_back`)。
- ビューの無い `Session` は、今までどおりデーモンの端末に操作を送る。

ペインのビュー自体は、タブを離れても作り直されずに残る。捨てるのは端末だけである。

### キーがデーモンのループを通らないことで生じた順序の問題

配色(プログラムの色の問い合わせに答えるための値)はデーモンのループが受け取る。
キーは、以前はこのループでエンコードされてから PTY へ行ったが、今はループを通らず
PTY へ行く。ループは PTY の出力を優先して読むので、負荷でループが遅れると、
後から打ったコマンドの問い合わせが、先に送った配色より先に処理された
(`a_program_that_asks_the_colors_is_told_the_ones_it_is_drawn_in` が、テストを
並列に走らせたときだけ古い色で落ちた)。PTY の出力を処理する前に、届いている配色を
先に適用するようにした。デーモンの端末に効くコマンドで、キーと順序が要るものは
他に見つけていないが、網羅して調べてはいない。

### 結果

- ワークスペースの全テスト(実際のシェル、実際のデーモンを通すものを含む):
  2388 件中 2385 件が通る。落ちる 3 件は上の「失敗した 3 件」と同じ。
- 状態を受け渡した後に同じバイト列を流す突き合わせ(72 通り): 画面、カーソル、
  タイトル、モードが 72/72 で一致。違いは古い履歴の残り行数だけ。
- 状態は画面が先に並ぶ。974KB の状態のうち先頭の 124KB で描ける端末になり、
  そこで切っても復元できる。
- 履歴が約 1 万行のときの状態: 3.1MB(120×40)と 6.4MB(240×70)。書き出し
  2.9ms / 6.7ms、読み込み 6.9ms / 14.7ms(release)。
- 大量出力(`yes flooding | head -n 3000000`、27MB)で、ビューを 1.5 秒止めて
  遅れさせたとき: ビューが受け取ったのは 2.1MB と状態 1 回で、最後の画面は
  シェルのものと一致し、その後の入力も通る
  (`a_flood_of_output_ends_with_the_screen_the_shell_has`。エンジンを
  `LIBGHOSTTY_VT_SYS_OPTIMIZE=ReleaseFast` でビルドして手で走らせる。既定の
  debug ビルドでは 60 秒に収まらない)。
- ビューが遅れない場合は 30MB すべてがビューへ流れる。止める条件は「ビューが
  遅れたか」だけで、量そのものには上限が無い。

### 確かめていないこと、決めていないこと

- 実際の窓での動作と体感。
- 大量出力をビューが全部取り込むときの、UI スレッドの負担。取り込みはレイアウトの
  中で起きる。
- 送り直しのあと、ビューの履歴は画面の近くの分しか無い。残りを後から埋める手段は
  組んでいない。
- 同期更新の保留(150ms)の時計が、デーモンとビューで別々に進む。ビューの側は
  次に取り込むときにしか保留を解かない。
