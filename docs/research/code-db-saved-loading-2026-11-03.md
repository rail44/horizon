# コードデータベース:読み込みの保存(2026-11-03)

[設計文書](../code-database-design.md)の「Saved loading (2026-11-03)」の測定と実験の記録である。`code-db` が毎回の起動でビューを生のまま定義し直していたのを、読み込み済みのデータベースを入力の状態ごとに保存して読み取り専用で付ける形に変えた。実装は `duckdb-ext/code-db/src/saved.rs`、利用者向けの説明は `duckdb-ext/sql/README.md` の「Saved loading」である。

## 経緯

オーナーの 2026-10-30 の方針(「make the schema simple enough for a refactoring agent to write its own queries, then dogfood finding refactoring targets」、設計文書の要約)に沿って、エージェントが自分でクエリを書いてリファクタリング対象を探す dogfood を行った。そのとき 1 問ごとに 15〜19 s かかり、問いを書き直しながら探す使い方の一番の障害だった。

## 固定費の内訳

キャッシュが揃った状態で `SELECT 1` だけを流しても 12.5 s かかった。ファイルと文ごとの所要時間を一時的な計測(コミットしていない)で取った。

| 箇所 | 所要時間 |
| --- | --- |
| `views/graph.sql` | 3.4〜7.2 s |
| `views/quality.sql`(うち `unit_quality` の CREATE 1 文が 4.2 s、`unit_fan_in` が 1.1 s) | 4.3〜7.6 s |
| `refresh.sql`(キャッシュへの付け替え) | 3.7〜8.2 s |
| 言語判定のための前半の読み込み(2 回目の `00_load.sql` から `views/terms.sql`) | 約 0.5〜1 s |

幅は 2 回の計測の差で、2 回目は機械の負荷が高かった。

切り分け:下位の層がキャッシュを向いた後に、`unit_quality` と同じ定義を別名で CREATE すると 25 ms で終わった。生のビューの上では 4.2 s である。固定費は、生のビューを入れ子のまま束縛することから来ている。今の鍵は `duckdb_views()` のビュー本文を含むので、鍵を作る前にすべてのビューを生のまま定義する必要があり、キャッシュが有効でもこの手順は省けなかった。

README の Cache の節には「a `code-db query` process spends 1–3.5 s loading」とあり、その後の作業(言語層、名前空間、表示名)で増えたものと見られる。増えた時期は調べていない。

## DuckDB 2.0.0 の振る舞いの確認

保存の形を決める前に、CLI(v2.0.0 d54cbbe3df)で確かめた。

| 試したこと | 結果 |
| --- | --- |
| 読み取り専用で 2 プロセスから同時に開く | 両方成功 |
| 読み取り専用の状態で一時テーブル・一時ビュー・変数 | 成功 |
| 書き込み中のファイルを別プロセスが読み取り専用で開く | 即座にロックエラー(待たない) |
| 読み取り専用で開かれている間に別プロセスが書き込みで開く | 即座にロックエラー |
| `-readonly` で起動して `CREATE SCHEMA` | 失敗。メモリ上のデータベースの追加も失敗 |
| メモリ上を主にして保存ファイルを `READ_ONLY` で追加し、修飾なしで保存側のビューを引く | 保存側のビューは自分のカタログの中で名前を解決する。別カタログ(`cache`)も名前で解決する |
| `SET search_path = 'memory.main,saved.main,saved.rust'` | 修飾なしの名前も `rust.units` も解決する |

鍵の違う二つの保存物が同じ `refresh.sql` のキャッシュファイルを共有すると、片方が読み取り専用で開いている間にもう片方の作成がロックエラーになる(`code-db shell` は開いている間ずっと保持する)。そのため、作成の最後にキャッシュファイルを保存物ごとの写しにし、読む側は写しだけを開く。

## 鍵から外す変数の確認

ビューのファイルが `getvariable` で読む変数は 19 個だった。`lang`、`exclude_patterns`、`include_untracked` はファイル一覧を絞り、その結果のファイル一覧(内容 ID つき)が鍵に入る。`languages` の上書きはファイルの集合を変えずに言語の割り当てだけを変えうるので、鍵に入れる必要がある。実装では、ビューのファイルが読む変数をファイルの本文から拾い、限界値 5 つと `cycle_edges` を除いてすべて鍵に入れた。`cycle_edges` は `refresh.sql` がキャッシュしない生のビューが問いの時点で読むだけで、鍵に入れると値を変えるたびに作り直し(約 20 s)が起きることを試験で確かめてから外した。

既存の鍵の漏れ:`refresh.sql` の鍵は sitting_duck の版を含むが、このワークスペースの拡張(`scip_index`、`git_history`)の版を含まない。デコーダを直して拡張を作り直しても、インデックスファイルが同じなら古いキャッシュが使われる。保存物の鍵には二つの拡張ファイルの内容を入れた。`refresh.sql` の鍵は変えていない(SQL の層は変えない、というオーナーの判断)。

## 検証

- **出力の一致**:変更前の `code-db`(HEAD cad3e2be から作った版)と変更後の版で、同じ木に対して 26 本を流した。12 のクエリ全部、引数を変えた 2 本、`FORMAT=csv` の 2 本、dogfood の自作クエリ 9 本、表示名スキーマを引く 1 本である。24 本はバイト単位で一致した。残る 2 本(`size` と自作の 1 本)は、すべての `ORDER BY` の鍵で同値の行の順だけが違った。`size` の同値の行の順は、変更前の版を 2 回流しても変わる(`ORDER BY loc DESC, path, start_line` で、一つのマクロが同じ行に複数の項目を定義する場合に順が決まらない)。
- **所要時間**(保存物がある場合):`SELECT 1` 2.6 s、`size` 3.1 s。作成はそれを走らせる 1 回に 20〜30 s を足す。
- **同時実行**:既存の保存物を読む 2 本と、新しい状態を要する 2 本を同時に起動した。読む 2 本は作成中に約 5 s で返り、作成の 2 本は順番に処理されて同じ結果を返し、それは変更前の版の出力とも一致した。保存物が揃った状態で同じ 4 本を同時に流すと、それぞれ 3〜4.5 s だった。
- **鮮度**:ビューのファイルにコメントを 1 行足すと新しい鍵で作り直され、古い保存物は掃除で消えた。
- **対話シェル**:`code-db shell` で `rust.units` を引け、利用者の `CREATE VIEW` はメモリ側に作られた。
- `duckdb-ext/check.sh` は通った。

## 残っていること

- 言語判定のための前半の読み込み(約 0.5〜1 s)は残っている。保存物から用語の対応を引けば省ける。
- `size` の同値の行の順が実行ごとに変わる。並べ替えの鍵に `unit_id` などを足せば決まる。
- 今の `code-db` は `refresh.sql` のキャッシュを書き込み可能で付けているのに、変更前の版を 2 本同時に流した 1 回の試行では衝突しなかった。理由は確かめていない。
