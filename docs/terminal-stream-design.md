# ターミナルの流れ — デーモンはバイト列を送り、ビューも端末を持つ

Status: 試作ブランチ `worktree-ghostty-vt-spike` で実装(2026-11-19)、main には未統合。
ワイヤの版は 22(現行値はコードの `TERMINAL_PROTOCOL_VERSION` を参照)。
測った数字と試した経緯は `docs/research/libghostty-vt-engine-spike-2026-11-19.md`。

## 何を決めたか

端末のエンジンを `alacritty_terminal` から libghostty-vt に替え、`horizon-terminald` と
ビューの間を次の形にした。

- デーモンは PTY を持ち、自分の端末(`TerminalCore`)に PTY の出力を通す。プログラムへの
  応答、ベル、タイトル、クリップボードへの書き込み(OSC 52)、通知、プログラム状態は、
  今までどおりデーモンの端末から出る。
- ビューが表示しているセッションには、デーモンが端末の状態を送り、その後はデーモンの
  端末が受け取ったバイト列を送る。ビュー(`src/terminal/session.rs` の `Session`)は
  同じ `TerminalCore` を手元に持ち、そこへ流れを取り込む。描くフレームは手元の端末から
  読む。
- デーモンはフレームを作らない。ワイヤにもフレームは無い。

この形にした理由: libghostty-vt の描画用の状態(行の番号と、変わった行の印)は、
同じプロセスの端末からしか作れず、外から中身を入れる口が無い。デーモンで作ったものを
ビューへ運べないので、ビューにも端末を持たせ、同じ入力(バイト列)を流す。

## 流れ

デーモンからビューへは、接続の events(順序が保たれ、取りこぼさない)に載せる
(`TerminalUpdate`)。

| 送るもの | 中身 |
|---|---|
| `State { bytes, more }` | 端末の状態(エンジンのスナップショット)。1MB ごとに分け、最後のものが `more: false` |
| `Output(bytes)` | デーモンの端末が受け取ったバイト列 |
| `Resized(size)` | リサイズ。デーモンの端末に適用した位置に入る |
| `HoldReleased` | デーモンの時計が同期更新の保留を解いた位置 |

ビューからデーモンへは、コマンド(`TerminalCommand`)。

| 送るもの | 意味 |
|---|---|
| `WantState` | 状態と、その後の流れを求める |
| `StopState` | 表示しなくなった。流れを止める |
| `OutputTaken(n)` | `Output` を n バイト取り込んだ |

- 流すのは「PTY から読んだまま」ではなく「デーモンのエンジンが受け取ったもの」である。
  コアは、自前で読む列(通知)かどうかが分かるまで、列の頭をエンジンに渡さずに持つ。
  状態を書き出した時点でその分はエンジンに入っておらず、次の `Output` で届く。この形で、
  出力のどのバイト位置で状態を渡しても、続きの画面が通しで書いた端末と一致する
  (`a_state_taken_between_any_two_bytes_goes_on_to_the_same_screen`)。
- 遅れたビュー: デーモンは、送って確認されていないバイト数を数える。2MB を超えたら送るのを
  止め、ビューが全部取り込んだと言ってきたところで、状態の「画面の部分」(スナップショットを
  画面の終わりで切ったもの)を送る。止めていた間のバイト列は送らない(状態に入っている)。
  その後、PTY の出力が 300ms 止まり、ビューが送った分を取り込んでいれば、状態の全体を
  1 回送って履歴を埋める。
  - 最初は全体を送り直していた。48,000 セルの画面で出力が続くと、300 フレーム中 211 回、
    約 4MB の状態を受け取り直し、その読み込み(1 回約 14ms)でまた遅れる循環になった。
    画面の部分にしてから、同じ条件で 1 フレームの中央値が 35.7ms から 21.5ms になった。
  - 全体が届くと、ビューの端末はそれで置き換わる。そのときの選択は消える。
- 同期更新の保留を時間切れ(150ms)で解く時計は、デーモンの 1 つだけ。デーモンが解いた
  位置に `HoldReleased` を入れ、ビューの端末はそこで解く。ビューは時計を持たない。
- 配色(プログラムが色を問い合わせたときの答え)はデーモンの端末に効く。キーはデーモンの
  ループを通らずに PTY へ行くので、ループは PTY の出力を読む前に、届いている配色を先に
  適用する。

## ビューの側

- 端末を手元に持つのは、ターミナルのビューが表示中のタブにある間だけ。タブを離れると
  端末を捨てて `StopState` を送り、戻ると `WantState` を送り直す。離れていた間の出力は
  状態に入っている。状態が届くまでは何も描かない。
- キー、文字、貼り付け、マウス報告、フォーカス、プログラム宛てのホイールは、手元の端末で
  バイト列にして `Input` で送る(`Session::input`)。リサイズと配色はデーモンへ送る。
  デーモンはキーや入力のコマンドを持たない(`Input` のバイト列だけを受け取る)。
- 手元に端末が無い間(状態が届く前、タブを離れている間)の入力は溜め、端末ができてから
  順に処理する。タブを離れるときは、溜めた入力のうちフォーカスの最後の 1 つだけを残す。
- 選択、コピー、履歴のスクロールと履歴の窓は手元の端末だけで済む。デーモンには何も送らない。

### 問い合わせへの応答とキーの順序

デーモンは、クライアントの `Input` を PTY に直接は書かず、セッションのループに通す。
ループは、PTY から届いている出力(プログラムの問い合わせ)を先に処理して応答を書き、
それからクライアントのバイト列を書く。応答とクライアントのバイト列は、ループから
PTY の書き込み役へ 1 本の流れで渡る。fish はプロンプトのたびに背景色を問い合わせる
(`OSC 11;?`)。応答より先に、次のプログラムを起動する Enter が PTY に書かれると、応答が
そのプログラムの入力になる(gh の対話プロンプトが壊れた不具合)。この順序は、キーを
デーモンがエンコードしていた頃はループが守っていた。キーを `Input` で送るようにした後、
デーモンが `Input` を直接 PTY に書いていたので一時的に守られていなかった
(`pending_query_is_answered_before_a_queued_keystroke_is_forwarded`)。

### キーのエンコード

キーはすべてエンジンのエンコーダが書く(`crates/horizon-terminal-core/src/core/keys.rs`)。
ビューはキーイベントから、物理キーの名前(UI Events の `KeyA` など)、修飾、押す・繰り返し・
離すの別、キーが作った文字を渡す。

- エンジンに名前の無いキー、入力メソッドの確定文字は、名前の無いキーに文字を添えて渡す。
  エンジンはどのモードでも文字をそのまま書く。
- 「Shift なしの文字」は、配列がビューに届いていないので、英字はその小文字、それ以外は
  US 配列でそのキーが作る文字で補う。US 配列以外で Shift と記号を押したときは正しくない。
- Ctrl+Shift+英字は、プログラムが何も頼んでいないとき(kitty のフラグなし、かつ xterm の
  modifyOtherKeys が 2 でない)は、Shift を外して Ctrl+英字として書く(`^A`)。
  - エンジンはここで kitty の形 `ESC[97;6u` を書く。Ghostty の作者はソースのコメントで、
    これは「ほとんどのターミナルと違い、一致するのは kitty だけ」の意図した逸脱だと
    書いている。bash 5.3 はこの列を文字として行に入れる(`7;6u` が入る)ことを確かめた。
  - xterm、Alacritty、WezTerm、foot、VTE、Konsole、Windows Terminal、rio、iTerm2 は `^A` を
    送る(各ソースの該当関数を読んだ調査。実物は動かしていない。Konsole、iTerm2、
    Windows Terminal は一部追い切れていない)。
  - modifyOtherKeys 1 でも `^A`(xterm と同じ)。2 では `CSI 27;6;65~`、kitty のフラグが
    あれば `CSI 97;6u`(エンジンのまま)。
  - エンジンは端末の modifyOtherKeys の状態を読む口を持たない。このキーに限り、端末の
    設定で書いた結果と、modifyOtherKeys 2 だけを切った設定で書いた結果を比べ、同じなら
    2 は効いていないと判断する(このキーでは 2 のときだけ結果が変わる)。

### 描く行

エンジンのセルから、描くための行(`TerminalLine`)を 1 回で組む(`core/render.rs`)。行は
次のものを持つ。

- フォントで描く文字列。空白のセル(空白、何も書かれていない、タブなどの制御文字、
  隠された文字)は文字列に入れず、列だけを数える。
- 文字列の各文字のバイト位置と列。全角は 2 列進み、結合文字は元の文字の列。
- 図形として描く文字(罫線、ブロック、六分割、点字)の位置と文字。文字列の中では空白に
  なっている。どの文字を図形で描くかはビューが決め、手元の端末を作るときに渡す
  (`TerminalCore::set_drawn_as_shapes`)。デーモンの端末には渡さない。
- 同じスタイルが続く範囲(バイトの範囲、列の範囲、スタイル)。行全体を覆う。

ビューは、この文字列と範囲をそのまま parley と背景・下線・図形に使い、組み直さない。
以前は、エンジンのセルから「スパン」(スパンごとの文字列とスタイル)を組み、描くときに
もう一度、文字列・色の範囲・列に組み直していた。フレームの型はワイヤに載らなくなった
ので、直列化もしない。

測った差(400×120 で 1 行スクロールするごとのフレームの組み立て): 4.1ms から約 3.1ms。
そのうちエンジンからセルを読む分は約 1.5ms で変わらない。

## ワイヤの版と、版のずれ

ワイヤの版は 22(`MIN_SUPPORTED` も 22)。版を上げたときは、ランタイムの再読み込みでは
なく Horizon の再起動が要る。デーモンとビューは同じビルドの libghostty-vt を使う前提で、
スナップショットの形式の互換は考えていない(合わなければデーモンを入れ替える)。版がずれた
ときに VT 列で状態を渡す代替は後回し。

## ビルド

libghostty-vt はクレートのビルドスクリプトが Zig 0.17 でソースからビルドする。リポジトリの
`.cargo/config.toml` の `[env]` で、すべてのプロファイルを ReleaseFast にしている。debug
ビルドのエンジンは出力の取り込みが約 1000 倍遅く(117KB に 926ms)、ビューは UI スレッドで
エンジンを動かすため。

## 捨てたもの

- デーモンのフレームの経路(`watch<TerminalFrame>`、フレームをまとめる間隔、
  `HORIZON_TERMINAL_FRAME_INTERVAL_MS`)。
- デーモン側の選択・コピー・履歴の窓(`SelectionStart`、`SelectionUpdate`、`CopySelection`、
  `RequestScrollWindow`、`ScrollWindow`)。履歴は手元の端末のビューポートを動かして見る
  (`docs/terminal-scrollback-design.md`、2026-11-22 に窓をやめた)。
- Horizon 自前のキーエンコーダ(`protocol/kitty_keyboard.rs`)と、その kitty の適合表。
  `docs/terminal-kitty-associated-text-design.md` の、確定文字を `CSI 0;1;…u` で送る部分も
  無くなった(エンジンは文字をそのまま書く)。
- シェルの cwd の読み直しのきっかけ: フレームが静かになった後だったのを、PTY の出力が
  200ms 静かになった後にした。
- フレームの到着時間を測る手動の計測(`crates/horizon-terminald/tests/latency_probe.rs`)。

## オーナーの判断

- 構成: 「ではYで設計や判断の続きをしていきましょうか」(2026-11-19)。
- 表示していないセッションは端末を持たない、キーをエンジンに任せる、版のずれは当面今の
  方針、試作ブランチの上で通しで組む: 「それぞれ推奨通りでよいです」(2026-11-19)。
- 送り直す状態を全体にする、時計をデーモンの 1 つにする、フレーム経路と自前エンコーダを
  消す、落ちていたテストをエンジンの応答に合わせる、ReleaseFast をリポジトリの設定に置く、
  この文書の名前: 「それぞれ推奨の形でよさそうです」(2026-11-19)。
- Ctrl+Shift+英字: 他のターミナルの調査の後、「はい。それで行きましょう。」(2026-11-19)。
- 描く行をセルから直接組む(上の「描く行」)と、遅れたビューには画面の部分を送り、
  落ち着いたら全体で履歴を埋める: 「1. A / 2. a」(2026-11-19)。
- デーモン宛てのキー・入力のコマンド(`Key`、`KeyInput`、`TextInput`、`Paste`、`Scroll`、
  `Mouse`、`Focus`)を消す: 「Aで」(2026-11-19)。

## 決めていないこと、既知の穴

- 大量出力をビューが全部取り込むときの UI スレッドの負担(取り込みはレイアウトの中で
  起きる)。遅れないビューには出力が全量流れる。48,000 セルの画面で出力が続くと、
  1 フレームは約 23ms かかる(取り込み、行の組み立て、整形、描画命令の組み立てがほぼ
  同じくらいずつ)。
- 描画命令の組み立て(48,000 セルで 1 フレーム約 5〜7ms)。Blitz のウィジェットは毎回
  シーンを最初から組むので、変わっていない行の分も毎フレーム組み直している。
- 出力がスクロールすると、エンジンは全行に変更の印を付けるので、1 行流れるだけでも全セルを
  読み直す(400×120 で約 1.5ms)。
- 遅れたビューに全体を送り直すとき、ビューの選択が消える。
- 実際の窓のキーイベントが、物理キーの名前と作られた文字をどう運ぶか(Ctrl を押したときの
  文字、日本語配列、テンキー)。
- `horizon-wire` のフレーム用の部品(`FRAME_MAX_ITEM_BYTES`、`CappedWatchReceiver`、
  それに合わせた `RTC_MAX_REPLY_BYTES`)の扱い。
- `horizon-terminal-core` に残る、旧エンジンを前提にしたコメント。
- 版がずれたときの VT 列での代替。
